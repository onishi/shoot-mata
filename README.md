# shoot-mata v02

AIエージェントが、企画から公開後の運用までを自律的に進め、完成品質のブラウザ向け横スクロールシューティングを作るプロジェクトです。

## 現在地

- `ver01/` は旧版のコード、素材、文書、ワークフローをそのまま保存した読み取り専用アーカイブです。
- 旧版は1ステージのMVPと公開・運用基盤まで到達しましたが、「多彩なステージ」「特徴的なパワーアップ」「完成品質のグラフィック」を満たさないまま全工程完了と誤判定しました。
- 旧GitHub Pagesが閲覧できる場合も、それはver01のMVP展示であり、v02の完成品または現行リリースとは扱いません。
- v02は旧版のコード、アセット、設定をコピーせず、設計から作り直します。`ver01/` は失敗の原因と検証方法を学ぶためにだけ参照します。
- 新しい成果物は今後 `ver02/` 以下へ作成します。ルートの方針文書はこのREADMEだけです。
- 2026-10-21のユーザー指示により、人間による主観評価は以後の進行ゲートから外します。機械判定、決定的シミュレーション、静的検査、ブラウザ計測で進め、楽しさ、操作感、聴感など未測定の主観品質を確認済みとは扱いません。

## 変えてはいけない製品目標

90年代アーケードシューティングを思わせる、懐かしくも新しいブラウザ向け横スクロールシューティングを完成させます。

完成版には、少なくとも次が必要です。

1. **4つ以上の完成したステージ**
   - 各ステージに固有の舞台、背景、展開、敵編成、ゲームプレイ上の仕掛け、ボスを用意する。
   - 色や敵の数を変えただけのステージは別ステージとして数えない。
   - 各ステージは単独で開始から結果・再挑戦まで遊べ、全体を通した進行も成立させる。
2. **ゲームの核になるパワーアップシステム**
   - プレイ感が異なる主武器を3系統以上用意する。
   - 各武器に3段階以上の機能的・視覚的な成長を用意する。
   - 強化の選択、組み合わせ、またはリスクと見返りが生じる仕組みを持たせる。
   - 一時的な必殺技や単純なWIDE／FOCUS切替だけを「特徴的なパワーアップ」の達成とは扱わない。
3. **完成品質のグラフィックと演出**
   - 自機、武器、敵、ボス、背景、UIに統一された完成アートを用意する。
   - ステージ固有の背景レイヤー、アニメーション、パララックス、攻撃・被弾・撃破・回収・登場・クリア演出を実装する。
   - 基本図形だけの仮表示やデバッグ表現を完成アートとして残さない。
4. **一本のゲームとしての完成度**
   - タイトル、導入、操作説明、ステージ進行、スコア、ポーズ、設定、結果、コンティニューまたは再挑戦、エンディングまでつなげる。
   - キーボードとタッチの双方でプレイでき、PC、縦長スマートフォン、横長スマートフォンに対応する。
   - 音楽、効果音、視覚フィードバック、難易度曲線、読みやすさ、アクセシビリティを製品全体で整える。
5. **独自性**
   - 90年代作品の表層的な模倣ではなく、パワーアップとステージ進行に本作固有の判断を生むフックを設計する。
   - 他作品のキャラクター、名称、画面、音、素材を複製しない。

これらは製品の必須要件です。AIエージェントの判断だけでMVP外、将来対応、バックログへ降格してはいけません。変更にはユーザーの明示的な承認が必要です。

## 「MVP」と「完成」の区別

- プロトタイプは、仮説を安く検証するための使い捨て可能な試作品です。
- MVPは、コアループを端から端まで検証するための内部マイルストーンです。
- バーティカルスライスは、1区間を完成品質にして制作方法を確立するものです。
- コンテンツ完成は、全ステージ、全主要システム、全必須アートが実装された状態です。
- 製品完成は、コンテンツ完成後にQAと最終検収を通過した状態です。

MVP、バーティカルスライス、公開可能な技術デモを、製品完成と呼んではいけません。フェーズ番号を最後まで消化しただけでも完成にはなりません。「完成」「全フェーズ完了」「リリース可能」という表現は、このREADMEの製品完成条件をすべて証拠付きで満たした場合だけ使います。

## 情報の優先順位

矛盾がある場合は、上から順に優先します。

1. ユーザーの最新の明示指示
2. このREADMEの製品目標と完成条件
3. `ver02/docs/02-product-requirements.md` の製品要件と受け入れ条件
4. フェーズ計画と個別仕様
5. バックログ、実装メモ、旧版資料

下位文書で上位の必須要件を縮小してはいけません。MVPの範囲を決めるときも、製品完成までに戻す項目と実装フェーズを必ず対応付けます。

## 開発フェーズとゲート

### 00. 旧版の反省と再調査

`ver01/` の失敗を分析し、ジャンル、競合作品、ブラウザ制約、独自性の候補を調査する。旧版を改修案の出発点にはしない。

完了条件：失敗原因、再発防止策、検証する仮説が文書化されている。

### 01. コンセプト

対象プレイヤー、感情的なゴール、90年代らしさ、本作固有の新しさ、一文コンセプトを定める。少なくとも3案を比較して選ぶ。

完了条件：プレイヤーが何を判断し、何に熟達し、なぜ繰り返すかを説明できる。

### 02. 製品要件と受け入れ条件

4ステージ以上を含む完成製品の全体像、ゲームループ、進行、難易度、パワーアップ、画面、音、保存、操作、対応環境を定義する。ここで内部検証用MVPも切り出すが、製品要件から消してはいけない。

完了条件：全必須要件が受け入れマトリクスにあり、実装予定フェーズと検証方法を持つ。

### 03. コアメカニクス試作

移動、射撃、敵、パワーアップの複数案を小さく試す。特徴的なパワーアップは最低3案を比較し、製品要件への適合、到達可能な構成、状態変化、代償の発生を再現可能な方法で評価する。

完了条件：採用するコアループとパワーアップの根拠が、操作可能な試作と比較結果で示されている。これは製品完成ではない。

### 04. アート・音・UX設計

ムードボードだけで終えず、最終品質を示す自機、敵、背景、UI、エフェクト、音の代表素材を作る。解像度、アニメーション、配色、コントラスト、命名、権利、生成素材の扱いを決める。

完了条件：ゲーム内で表示した代表シーンが最終品質の基準として承認でき、残りの素材を同じ工程で制作できる。

### 05. 技術基盤

描画、入力、音、ステージデータ、セーブ、テスト、ビルド、CI、公開方式を設計する。コンテンツをデータ駆動で追加できる構造を作る。

完了条件：完成製品の規模を支えられる設計と自動テスト基盤があり、仮の1区間を動かせる。

### 06. バーティカルスライス

1ステージの代表区間を、完成アート、完成音、完成パワーアップ、ボス、UIまで含む製品品質へ仕上げる。

完了条件：品質基準と制作コストを確認できる。残り3ステージ以上の制作が必須であり、この時点では公開工程へ進まない。

### 07. コンテンツ制作

ステージを1つずつ独立したスライスとして制作する。各スライスで背景、仕掛け、敵、ボス、音、難易度、テスト、ブラウザ確認まで完了させる。パワーアップの全系統・全段階もここで揃える。

完了条件：4ステージ以上、全パワーアップ、導入からエンディングまでが実装され、仮素材が必須経路に残っていない。

### 08. コンテンツ完成アルファ

全体を通して、進行不能、状態初期化、保存、操作、レイアウト、音、性能を検証する。不足コンテンツの追加をバックログへ逃がさない。

完了条件：全必須コンテンツが存在し、開始からエンディングまで複数回完走できる。

### 09. ポリッシュとベータ

難易度曲線、テンポ、視認性、入力感、演出、音量、アクセシビリティ、ブラウザ差を調整する。AIテストは再現性のある不具合発見に使い、人の主観と同一視しない。

完了条件：重大な既知不具合がなく、品質目標と残存リスクが記録されている。

### 10. 最終検収

受け入れマトリクスを製品要件まで一項目ずつ照合する。MVP条件だけの照合は禁止する。

完了条件：このREADMEの必須要件と製品要件がすべて合格し、未達の中核要件が0件である。

### 11. 公開

リリース候補だけを本番公開し、公開URLで全ステージの主要フロー、アセット、メタデータ、権利通知、データ取扱い、ロールバックを確認する。

完了条件：本番で製品版を確認し、バージョン付きリリースノートと復旧手順がある。

### 12. 運用

公開後の障害、互換性、性能、依存関係、権利条件、改善要望を管理する。運用フェーズを不足コンテンツの代替に使わない。

完了条件：監視と更新手順が動作し、修正・改善・新機能が優先順位付きで管理されている。

## 必須ゲート

- Phase 02終了時：製品要件の各項目に実装フェーズが割り当てられている。
- Phase 03終了時：パワーアップの複数案を同一条件の決定的シミュレーションで比較し、採否を再現できる。
- Phase 04終了時：基本図形ではない最終品質の代表シーンをゲーム内で確認している。
- Phase 06終了時：バーティカルスライスの品質を確認し、残りのコンテンツ量を再見積もりしている。
- Phase 07終了時：4ステージ以上と全パワーアップが存在する。未達ならPhase 08へ進まない。
- Phase 10終了時：MVPではなく製品要件の受け入れマトリクスが全件合格している。
- Phase 11終了時：本番公開物がPhase 10で合格したものと一致する。

ゲート未達時は次へ進まず、必要な作業を同じフェーズに追加します。フェーズを完了させるために条件を弱めてはいけません。

## AIエージェントの作業ルール

ユーザーから「README.md および各種ドキュメントに沿って開発を進めて」と指示されたら、次の手順で自律的に続行します。

1. このREADME、`ver02/docs/`、現在フェーズの `PLAN.md`、git状態を読む。
2. 受け入れマトリクスから未達の最優先項目を選ぶ。文書だけを増やし続けず、安全に実装できる範囲まで進める。
3. 作業前に目的、変更対象、完了条件、確認方法を短く示す。
4. 小さな動作単位で実装し、1タスクにつき1コミットにする。フェーズ終了時はpushする。
5. ロジック変更は自動テスト、UI変更は複数画面サイズのスクリーンショット、操作変更は実ブラウザ操作、ステージ変更は開始から結果までの通し確認を行う。
6. 不具合は再現条件、原因、修正、回帰テストを記録する。
7. 新しい案はバックログへ記録する。ただし、このREADMEの必須要件はバックログへ移さない。
8. 既存のユーザー変更を保護し、破壊的操作や外部への公開は対象と手順を確認する。
9. 確認できない主観的品質を「確認済み」と書かない。代替検証と限界を分ける。
10. 各スライス終了時に成果物、テスト結果、未達、仕様差、次の作業を `log.md` へ記録する。
11. 前回完了した作業を繰り返さず、現在の未完了地点から続ける。通常の技術選択は合理的に仮定し、重大な方向変更だけをユーザーへ確認する。

## 検証の最低条件

- ユニットテスト、統合テスト、決定的な通しプレイを用意する。
- PC、幅320〜390pxの縦長、横長スマートフォン相当で確認する。
- キーボード、タッチ、ポーズ、復帰、結果、再挑戦、ステージ遷移、保存復元を確認する。
- 各ステージを通常操作または説明可能な自動操作で完走し、固有要素とボスを確認する。
- 完成アートの一覧とゲーム内表示を照合し、仮素材が残っていないことを確認する。
- ビルド、配信容量、主要なパフォーマンス指標、コンソールエラー、外部通信、依存脆弱性を確認する。
- 使用素材、フォント、音、生成物、依存コードの権利と通知を確認する。
