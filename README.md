# Autonomous Game Foundry

このリポジトリは、AIが企画、実装、検証、批評、改善、公開、制作工程そのものの振り返りまでを自律的に繰り返し、メジャーバージョンごとに異なる完成品質の新作ゲームを作るための作業場である。

人間が繰り返し与える指示は、原則として次の一文だけでよい。

> README.mdおよび各種ドキュメントに沿って、自律的にゲーム開発を進めてください

AIは質問や承認待ちで通常作業を止めず、現在地を復元し、その時点で最も価値の高い作業を選び、実装・検証・記録・コミットまで進める。

## バージョンの考え方

- `verNN/`は完全新作となるメジャーバージョン`NN.0`である。次に作るメジャーバージョンは、存在する最大番号の次とする。
- `verNN.1/`、`verNN.2/`のようなディレクトリは、同じゲームを批評して磨くマイナーバージョンである。直前版は変更せず、検証可能なスナップショットとして残す。
- メジャー開始時は、ジャンル、テーマ、中核メカニクス、表現、規模をAI自身が決める。横スクロールシューティングを前提にしない。
- `verNN.0`の通しが成功しただけではメジャー版を終了しない。独立した批評と改善を原則2回以上行い、最終マイナー版をそのゲームの完成版とする。
- 現在のゲームが十分に磨かれ、公開確認とメジャー終了時の振り返りまで完了した場合だけ、次のメジャーバージョンへ進む。
- 過去版は完成作品と学習の証拠として保持する。修正対象は現在版だけに限定する。
- ルートREADMEは全バージョン共通の最上位方針である。現在版の古い設計や完成条件と競合した場合は、このREADMEを優先して設計を更新する。

## 新作の独立性

新しいメジャーバージョンでは、過去ゲームのコード、画像、音、文章、固有名詞、世界観、ステージ、数値、画面構成、ゲームシステムをコピーまたは改変して使わない。企画中も過去ゲームの内容を発想の出発点にせず、白紙から考える。

再利用してよいのは、このREADMEに集約した一般的な制作ノウハウ、標準的なアルゴリズム、開発ツール、テスト手法、公開の仕組みだけである。偶然ジャンルや題材が似ることは禁止しないが、過去版との差分を作ることを目的にはしない。

素材はメジャーバージョンごとにすべて新規制作する。AIが生成した画像・音、手続き生成、自作SVG・Canvas描画などを利用できる。外部素材を使う場合は権利と出典が明確なものに限り、素材台帳へ記録する。マイナーバージョン内では、同じゲームの素材を改善して継承してよい。

## 更新可能な品質基準

現在の総合基準作品は`ver04.2`とする。これは最初の基準であって固定された上限ではない。M6の比較で新しい完成版が総合的に上回ったことを証明できた場合は、この節の総合基準作品をその版へ更新し、以後は新しい基準を使う。

基準作品の内容、コード、素材、ジャンルを参照元や土台にはしない。比較するのは、次のような到達水準と制作証拠である。

- 約20分前後を通して中核メカニクスが導入、発展、組み合わせ、最終試験まで変化する製品密度
- 複数の固有環境、攻略対象、山場、最終局面を持ち、一つの短い仕掛けの反復で終わらないキャンペーン
- 背景、主要キャラクター、目標、危険、UI、エフェクト、音楽、効果音が同じ表現方針で作られた完成画面
- 初回導線、難易度差、失敗後の復帰、成長または習熟、設定、保存、ポーズ、結果、終演までつながる製品性
- 多数seedの通し、主要分岐と失敗経路、性能、音量、保存、アクセシビリティ、全主要画面の目視を含む検証深度
- 配布物の生成だけでなく、公開先での起動、版表示、主要経路、旧版保持まで確認したリリース品質

新作が短編に適したジャンルであっても、単純にプレイ時間を水増ししない。その代わり、ルールの組み合わせ、複数の有効戦略、再挑戦価値、物語分岐、生成性などにより、現行基準と比較できる体験の厚みを設計する。ファイル数、コード量、素材数だけを完成度の代理にしてはならない。

新作が一部の評価軸で最高水準に達したが、総合的には現行基準を置き換えない場合、その版を「アート」「初回導線」「戦略性」「アクセシビリティ」などの部門別基準としてこの節へ追記できる。次作は総合基準を下回らないことに加え、関連する部門別基準も比較対象にする。

## 新メジャーバージョンの始め方

まだ作業中の版がなければ、最初の実行で次の順に着手する。

1. 互いにジャンルと遊びが異なる企画を3案以上出す。
2. 独自の楽しさ、操作から生まれる判断、実現可能性、視覚・音響の魅力、繰り返し遊ぶ価値、検証しやすさで比較する。
3. 最も強い1案をAI自身が採用し、一文で説明できる中核体験と、作らないものを定める。
4. 現行の総合基準以上の厚みへ到達するため、想定プレイ時間、固有コンテンツ、メカニクスの発展段階、山場、表現、音、検証、公開までを「製品規模契約」として固定する。実装都合だけで後から縮小しない。
5. 新しい`verNN/`を作り、製品設計、ゲーム設計、アート・音響方針、技術設計、品質計画、`status.md`、`log.md`を置く。
6. 文書だけで終えず、中核体験を最短で検証できるプレイ可能な縦切りへ進む。

ゲームはPC版Chromeで直接遊べるブラウザゲームを基本とする。ジャンルに適するなら、アクション、パズル、戦略、探索、リズム、シミュレーション、物語ゲーム、またはそれらの融合を自由に選べる。キーボードを必須入力とし、必要に応じてマウス、ゲームパッド、タッチにも対応する。

## 各版に必要な状態管理

ディレクトリ構成は企画に合わせて決めてよいが、現在版には最低限次を置く。

```text
verNN[.x]/
  README.md
  docs/
    00-product-brief.md
    01-game-design.md
    02-art-and-audio-direction.md
    03-technical-design.md
    04-quality-plan.md
    05-major-retrospective.md  # メジャー終了時に作成
    acceptance-matrix.md
    agent-history.md
    asset-inventory.md
    decisions.md
    status.md
    log.md
  game/
```

- `README.md`: 作品名、中核体験、起動方法、現在地。
- `status.md`: 唯一の正とする進捗、完成条件、証拠、未解決課題、次の最優先作業。
- `log.md`: 日付順の判断、変更、失敗、検証結果。
- `05-major-retrospective.md`: 最終版と過去の基準作品を比較し、作品と自律開発ループの両方を評価したメジャー終了報告。
- `acceptance-matrix.md`: 製品規模契約と完成ゲートの全項目を、実装、テスト、実操作、画面・音、配布物、公開URLへ対応付ける追跡表。
- `agent-history.md`: 各自律実行を起動したエージェントとスクリプト、作業、検証結果、コミット件名を追跡する。
- `asset-inventory.md`: 背景、キャラクター、UI、エフェクト、音楽、効果音について、用途、制作方法、権利、完成状態、ゲーム内確認先を管理する。
- `decisions.md`: 重要な選択、比較した代替案、採用理由、予想した効果、後の検証結果を残す。
- 設計文書: 固定仕様ではなく、プレイ検証で更新する仮説。要件を変えた理由を記録する。

`acceptance-matrix.md`の各行には安定したIDを付ける。チェックだけで完了にせず、証拠ファイルまたは再実行可能なコマンドを記載する。MVPや途中マイルストーンで延期した製品要件は削除せず、担当段階を明記する。

## 実行エージェントの来歴

`run-codex-loop.sh`と`run-claude-loop.sh`は、次の環境変数を各実行へ渡す。

- `SHOOT_MATA_AGENT_LOOP`: `codex`または`claude`
- `SHOOT_MATA_AGENT_SCRIPT`: 起動したシェルスクリプト名
- `SHOOT_MATA_AGENT_RUN_NUMBER`: そのループ内の実行番号
- `SHOOT_MATA_AGENT_RUN_STARTED_AT`: 実行開始時刻

各実行は対象版の`docs/agent-history.md`へ次の形式で1行を追加し、同じ内容の要約を`docs/log.md`にも残す。

```md
| 開始時刻 | Agent | Script | Run | 作業・結果 | 検証 | Commit subject |
| --- | --- | --- | ---: | --- | --- | --- |
| 2026-11-06T20:00:00+0900 | Codex | run-codex-loop.sh | 3 | Stage 2を実装 | verify合格 | feat(ver12): add stage 2 |
```

各コミット本文の末尾には、実行元を機械的に検索できるよう次のtrailerを付ける。

```text
Agent-Loop: codex
Agent-Script: run-codex-loop.sh
```

Claudeの場合は`claude`と`run-claude-loop.sh`を使う。一つの実行で複数コミットを作る場合はすべてに付ける。環境変数がない対話実行では、スクリプトを推測せず`Agent-Loop: interactive`、`Agent-Script: none`と記録する。追跡導入前の過去版や過去コミットも、確実な証拠がなければ推測で埋めず`unknown`とする。

開発段階は原則として次の順に進める。

| 段階 | 目的 | 次へ進む条件 |
| --- | --- | --- |
| M0 企画・規模契約 | 白紙企画、対象体験、製品規模、非目標を決める | 現行基準の各項目に規模、担当段階、検証方法が割り当てられ、受入追跡表に未割当がない |
| M1 中核縦切り | 最小構成で独自の面白さを証明する | 実操作で判断、失敗、上達が発生する |
| M2 製品基盤 | 導入、設定、保存、復帰と制作規格を確立する | 仮素材なしの代表区間が完成品質になる |
| M3 本編制作 | 固有コンテンツとメカニクスを段階的に発展させる | 規模契約を削らず、開始から終演まで到達できる |
| M4 深度・表現拡張 | 単調さを除き、攻略、演出、音、再挑戦価値を深める | 全区間が固有の役割を持ち、短い試作感がなくなる |
| M5 批評・改善・公開 | 原則2回以上のマイナー改善と製品監査を行う | 完成ゲート、公開確認、旧版保持確認がすべて合格する |
| M6 メジャー振り返り | 作品と自律開発ループを比較評価し、ルート方針を改善する | 振り返り、README改善、最終コミットが完了する |

## 1回の自律実行プロトコル

1. **復元**: ルートREADME、現在版のREADME・`status.md`・最新ログ、`agent-history.md`、git状態を読む。`SHOOT_MATA_AGENT_*`から今回の実行元を確定し、中断中の変更を重複させない。
2. **選択**: 現在のM0〜M6、未達の完成条件、製品規模契約、実際のプレイ品質から、体験への効果が最大の課題を1つ選ぶ。安全に実装できることを質問に置き換えない。
3. **制作**: 動作する縦切りとしてコード、データ、素材、テストを更新する。不具合修正には可能な限り回帰テストを付ける。
4. **体験**: 実際にブラウザで遊ぶか自動操縦し、主要画面のスクリーンショットをAI自身が見る。数値だけで面白さや見栄えを判定しない。
5. **検証**: 関連テスト、ビルド、通しプレイ、性能、音量、保存、入力を変更リスクに応じて確認する。重大な欠陥は同じ実行内で直して再検証する。
6. **記録**: `status.md`、`log.md`、`agent-history.md`、受入追跡表へ、実行元、結果、証拠、残課題、仕様差、次に行う具体的な1作業を残す。段階を終える場合は、目的、変更ファイル、完了事項、検証結果、未確認事項、仕様変更と理由、次作業を短い完了報告として残す。
7. **保存**: 検証済みの意味ある単位を、実行元trailer付きでコミットする。公開設定が整っている場合は、完成ゲートを通った版だけを公開し公開物も確認する。

調査や計画だけが必要な段階を除き、1回を文書更新だけで終えない。反対に、未検証の大量実装を「完成」と記録しない。ユーザーの未コミット変更は保持し、無関係な変更を混ぜない。

## 制作で活用するノウハウ

- 最初の数十秒で中核の面白さを操作として伝え、説明文に依存しない。
- 入力には即時の視覚・音響フィードバックを返す。
- 新要素は単独で理解させ、組み合わせで応用させ、終盤で習熟を試す。
- 難しさを体力や物量だけで作らず、予告、位置取り、優先順位、リスクと報酬で攻略を作る。
- ゲーム規則と描画を分離し、固定時間刻みと決定的入力で高速・再現可能に検証する。
- ステージ、レベル、敵、会話などは可能な範囲でデータ駆動にする。
- 自動テストと自動操縦は到達性、回帰、所要時間、密度の検査に使い、人間相当の画面評価とプレイ批評を併用する。
- 初見検証は新規保存、状態注入なし、攻略専用ショートカットなしで開始する。開発者が正解を知る自動通しだけを、理解しやすさの証拠にしない。
- 外部プレイヤーを利用できない場合も改善を止めず、初見相当の入力制限、複数の自動方針、失敗ログ、無操作・誤操作、異なるseedによる代替実験を設計する。測れない主観は未確認と明記する。
- ジャンルが許す限り、少なくとも複数の有効戦略、解法、構成、難易度またはプレイ方針を比較する。一つの固定解を自動操縦が成功しただけで、深さや再挑戦価値を合格にしない。
- 仮素材は試作中だけ許可し、完成版からデバッグ表示、無意味な代用図形、未調整素材を除く。
- 単純なCanvas図形だけで全編を済ませる場合も、それが意図した完成表現であることを画面比較で証明する。制作の速さを理由に、背景、キャラクター、動き、エフェクト、音の固有性を省略しない。
- アクセシビリティ、ポーズ、再開、保存、音量設定、初回説明、失敗後の復帰を製品の一部として扱う。
- `npm run verify`など、ビルド・テスト・監査をまとめて再実行できる入口を用意する。

## メジャー版の完成ゲート

企画時にジャンル固有の基準を追加し、少なくとも以下をすべて満たした場合だけ完成とする。最初の通し成功、6区間の実装、配布物生成、テスト全件合格のいずれか一つだけで完成としてはならない。

- タイトルから主要な終着点まで、通常操作と自動検証の両方で到達できる。
- 中核メカニクスが複数の意味ある判断と有効戦略を生み、導入、発展、組み合わせ、最終試験の4段階以上で変化する。
- 操作、ルール、危険、目的、結果がプレイ中に理解できる。
- 主要コンテンツに固有の環境、判断、攻略、見せ場があり、座標や速度だけを変えた反復や量だけの水増しになっていない。
- 少なくとも二つの大きな山場と、既習要素を再構成する最終局面がある。
- 初見プレイ、慣れたプレイ、異なる戦略または難易度で、体験や判断に意味のある差が生じる。
- 新規制作した背景、主要キャラクター、UI、エフェクト、音楽、効果音が一貫した方向性を持ち、仮素材や無音の主要場面が残っていない。
- 最初の30秒、通常区間、全固有環境、全山場、最終局面、結果、終演を画像として採取し、AIが比較目視している。
- 単体・統合・通しテストに加え、複数seedまたは複数戦略の反復、代表的な性能・音量計測、保存破損、失敗・再挑戦・ポーズ・復帰を検証している。
- クラッシュ、進行不能、入力不能、保存破損、重大な音量・視認性問題がない。
- 原則2回以上の独立した自己批評で、初回理解だけでなく、深さ、テンポ、戦略、演出、音、終盤の満足度を実際に改善している。
- 現行の総合基準・関連する部門別基準と最終候補を同じ評価軸で比較し、規模が小さい場合は別の深さで同等以上の価値があると証拠付きで説明できる。
- 最終配布物を公開し、公開URLの起動、版表示、主要経路、旧版URLを確認している。権限不足時は未公開を完成とせず、阻害要因として残す。
- 受入追跡表の全必須IDが、実装、再実行可能な検証、目視または聴覚の代替証拠、最終配布物へ結び付いている。
- クリーン環境で依存関係を固定してbuildとverifyを再実行し、ローカルの古い`dist`や証拠ファイルへ暗黙依存していない。
- 配布物のファイル一覧とハッシュを記録し、検証した候補と公開物が一致する。旧版保持とrollback方法も確認する。
- 起動方法、操作、検証結果、既知の制約が文書化されている。

完成状態は次の語を区別する。

- **Prototype**: 中核仮説だけを試せる。製品完成ではない。
- **Vertical Slice**: 代表区間が完成品質。残りの本編は未完成。
- **Content Complete**: 規模契約の本編と素材が揃ったが、横断調整と最終監査前。
- **Release Candidate**: 完成ゲートをローカルで通った公開候補。未公開なら製品完成ではない。
- **Published Product**: 候補と同一の公開物を実URLで確認済み。
- **Major Closed**: 原則2回以上の改善、公開、M6振り返り、ルートREADME改善まで完了。次メジャーへ進める唯一の状態。

## マイナー版と次の新作

`verNN.0`の本編がつながったら、少なくとも一度は体系的に自己批評する。最初の30秒、テンポ、反復、選択の偏り、理解しにくさ、攻略の単調さ、画面の読みやすさ、音と手触り、性能、終盤の満足度を証拠とともに評価する。

直前版を新しい`verNN.x/`へ複製し、証拠上の効果が高い3〜5件へ絞って改善する。原則として、最初のマイナー版では理解、操作、視認性、テンポを、次のマイナー版では戦略の深さ、コンテンツ差、アート、音、終盤、再挑戦価値を批評する。問題がなかったという結論も、通し、画像、計測、比較を伴わなければ改善回数に数えない。

各マイナー版の開始前に、直前版の通し時間、成功・失敗、選択率、主要画面、性能、音量、テスト、既知課題をbaselineとして固定し、改善後も維持すべき品質を「非退行条件」として列挙する。新しい改善が既存の長所を壊した場合は完了せず、修正または明示的な優位性の比較まで行う。

実装が難しい、予定より大きい、テストが通った、6区間作った、配布物が小さい、次の企画を思いついた、という理由で改善を打ち切らない。残る課題が好みの範囲に限定され、完成ゲートと現行基準との比較に合格して初めてM5を終了する。

## M6 メジャー終了時の振り返りとループ改善

最終マイナー版の公開確認後、次のメジャー版を作る前に必ず独立した1回以上の実行をM6へ使う。実装を追加する回ではなく、完成作品と自律開発の方法を監査し、次の制作能力を高める回とする。

1. 最終版、現行の総合基準作品、関連する部門別基準、直近2つのメジャー完成版を、製品規模、中核の独自性、判断の深さ、コンテンツ差、最初の30秒、テンポ、アート、音、演出、終盤、再挑戦価値、アクセシビリティ、検証深度、公開品質で比較する。`ver04.2`が総合基準でなくなった後も、初期アンカーとして必要に応じて比較へ残す。
2. 「よかった点」「現行基準を超えた点」「現行基準より後退した点」「小さく安全にまとめすぎた点」「自動テストでは見逃した点」を、画像、計測、通し結果、実装事実と結び付ける。
3. 企画選定、規模契約、マイルストーン、完成ゲート、批評方法、テスト、素材制作、公開のどこが結果を生んだかを原因まで掘り下げる。
4. 新作が現行基準を総合的に上回り、製品性、検証、公開品質に重大な後退がない場合は、この節の総合基準作品を新作の最終版へ更新する。特定軸だけを明確に上回った場合は部門別基準へ追加する。昇格理由と比較証拠を振り返り文書へ残す。
5. 再発しうる問題と再利用できる成功だけを一般化し、ルート`README.md`の指示、基準作品、段階、チェック項目を実際に更新する。作品固有の設定や数値は持ち込まない。
6. 完成版の`docs/05-major-retrospective.md`、`status.md`、`log.md`へ比較結果、基準の昇格判断、README変更内容、変更理由を記録する。READMEを変えない場合も、現行ループと基準で十分な理由を証拠付きで残す。
7. ルートREADME、振り返り文書、状態記録を検証して一つの明確なコミットにする。そのコミット後だけ`ver(NN+1)/`を開始できる。

M6でREADMEを更新することは、過去作品のコードや素材を次作へ流用することではない。制作方法を経験から改善するための必須工程である。README変更によって現在の自律ループが自分自身を際限なく緩和しないよう、完成ゲートの削除や縮小には、それ以上に厳密でジャンルに適した代替基準と比較証拠を必須とする。

## ループの実行

CodexまたはClaude Codeを使い、既定で12回、30分間隔で進める。

```sh
./run-codex-loop.sh [run-count] [wait-minutes]
./run-claude-loop.sh [run-count] [wait-minutes]
```

例: `./run-codex-loop.sh 5 10`。各回は独立したエージェント実行で、失敗時は後続を止める。引数と環境は`--help`で確認できる。

## AIが止まってよい条件

通常の企画、命名、技術選定、素材方針、難易度調整、批評、次版への移行判断では止まらない。必要な認証・権限がない、ユーザー変更と安全に分離できない、回復困難な外部操作が必要、または外部障害が続きローカル作業も尽きた場合だけ、阻害要因と再開条件を具体的に報告する。
