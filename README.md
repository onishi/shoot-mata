# Autonomous Game Foundry

このリポジトリは、AIが企画、実装、検証、批評、改善、公開、制作工程そのものの振り返りまでを自律的に繰り返し、メジャーバージョンごとに異なる完成品質の新作ゲームを作るための作業場である。

人間が繰り返し与える指示は、原則として次の一文だけでよい。

> README.mdおよび各種ドキュメントに沿って、自律的にゲーム開発を進めてください

AIは質問や承認待ちで通常作業を止めず、現在地を復元し、その時点で最も価値の高い作業を選び、実装・検証・記録・コミットまで進める。

## バージョンの考え方

- `verNN/`は完全新作となるメジャーバージョン`NN.0`である。次に作るメジャーバージョンは、存在する最大番号の次とする。
- `verNN.1/`、`verNN.2/`のようなディレクトリは、同じゲームを批評して磨くマイナーバージョンである。直前版は変更せず、検証可能なスナップショットとして残す。
- メジャー開始時は、ジャンル、テーマ、中核メカニクス、表現、規模をAI自身が決める。横スクロールシューティングを前提にしない。
- `verNN.0`の通しが成功しただけではメジャー版を終了しない。独立した批評と改善を原則2回以上行い、最終マイナー版をそのゲームの完成版とする。
- 現在のゲームが十分に磨かれ、公開確認とメジャー終了時の振り返りまで完了した場合だけ、次のメジャーバージョンへ進む。
- 過去版は完成作品と学習の証拠として保持する。修正対象は現在版だけに限定する。
- ルートREADMEは全バージョン共通の最上位方針である。現在版の古い設計や完成条件と競合した場合は、このREADMEを優先して設計を更新する。

## 新作の独立性

新しいメジャーバージョンの独立性は、過去作と異なる結果を強制することではなく、過去ゲームの内容を企画・設計の参考や発想の出発点にせず、白紙から「今回いちばん作る価値があるゲーム」を考えることで守る。

白紙から考えた結果として、シューティングを再び選ぶこと、過去作と同じジャンルになること、一般的なゲームメカニクス、題材、画面構成が似ることは問題ない。過去作との差分を作るために有力な案を不自然に避けず、類似の有無ではなく、その企画単独の面白さと完成度で採否を決める。

ただし、過去ゲームのコード、画像、音、文章、固有名詞、世界観、ステージデータ、数値を直接コピーしたり、名前や定数だけ変えて流用したりしない。再利用してよいのは、このREADMEに集約した一般的な制作ノウハウ、標準的なアルゴリズム、開発ツール、テスト手法、公開の仕組みである。一般的な処理は新作に必要な形で新規実装してよい。

素材はメジャーバージョンごとにすべて新規制作する。AIが生成した画像・音、手続き生成、自作SVG・Canvas描画などを利用できる。外部素材を使う場合は権利と出典が明確なものに限り、素材台帳へ記録する。マイナーバージョン内では、同じゲームの素材を改善して継承してよい。

## 完成品品質の基準

ゲームジャンル、入力方式、画面比率、プレイ時間は企画に合わせて選ぶ。コイン投入、アトラクト、コンティニュー、ランキング、4:3画面など、実筐体を模した形式は全作品へ一律に要求しない。一方、1995年前後のアーケードゲームを意識した新作を作るという創作上の制約は維持する。必要なのは筐体手続きの再現ではなく、現代のプレイヤーが単体の完成作品として触れたときに、遊び、表現、手触り、展開へ対価を払う価値を感じられることである。

### 完成度を判断する原則

- 最初の操作から、入力、画面変化、音、結果が気持ちよく結び付く。ルールの独自性だけでなく、移動、攻撃、選択、成功、失敗そのものに触覚的な説得力を持たせる。
- タイトルまたは最初のプレイ画面に、作品固有の主役、世界、目標、動きが見える。機能上識別できるだけの図形、汎用UI、説明文の多さを完成表現の代わりにしない。
- 背景、キャラクター、敵、UI、エフェクト、アニメーション、音楽、効果音を同じ表現方針で作り、静止画だけでなく動作中の重さ、速度、衝突、破壊、成功の強弱を演出する。
- 本編の進行に伴い、数値、座標、色、敵の組み合わせだけでなく、空間、目的、操作の意味、攻略、テンポ、見せ場のいずれかが大きく変わる。同じ舞台と同じ行為を区切り数で水増ししない。
- ボスや終盤は通常区間の耐久力違いにせず、画面構造、行動規則、演出、攻略手順を再構成し、そこまで遊んだ時間に見合う驚きと決着を作る。
- 初見理解、アクセシビリティ、設定、保存、公開は品質の土台として必要だが、それらの有無やテスト件数を面白さ、商品性、アート品質の証拠にしない。
- プレイ時間、敵数、ステージ数、素材数、効果音数、画面数、配布経路数は制作事実であり、体感上の密度や完成度そのものではない。数を評価へ使う場合は、実プレイで生じる差を併記する。

各メジャー版はM0で、作品固有の「完成したときにプレイヤーへ売りになる体験」を3〜5項目に絞り、`acceptance-matrix.md`へ実プレイ、動作中の画面、比較対象を含む検証方法とともに置く。M1、M2、M4、M5では次の問いへ証拠付きで答える。

> この作品を知らない人が短い紹介や最初のプレイを見たとき、何に惹かれ、触ると何が気持ちよく、進めると何が変わり、なぜ最後まで遊びたいと思うか。

答えが機能一覧、設定、物量、テスト結果だけになる場合は未達である。自動検証は壊れていないことを証明できるが、面白さ、見栄え、手触り、驚きの合格判定は、実プレイと動作中の比較批評で行う。

## 1995年前後のアーケードゲームという創作基準

各メジャー版は、シューティング、横スクロールアクション、対戦格闘、ベルトスクロールアクション、パズル、レース、スポーツ、ガンゲーム、体感ゲーム、またはその融合など、1990年代のゲームセンターで発展した遊びと表現を意識する。既存作品のキャラクター、名称、画面、音、意匠を模倣せず、当時に存在し得た未知の新作という方向で独自に設計する。

この基準はブラウザ上に筐体を再現する指示ではない。コイン、クレジット、アトラクト、ランキング、4:3、少数ボタンは、企画に効果がある場合だけ採用する。評価するのは次の性質である。

- 操作してすぐ反応と目的が伝わり、短時間でも判断、危険、成功、上達を味わえる。
- 主役、敵、攻撃、地形、アイテムに遠目でも判別できる強いシルエットと役割があり、画面に一目で分かる見せ場がある。
- 移動、攻撃、命中、被害、撃破、決着に、誇張されたアニメーション、停止、反動、拡大縮小、画面効果、音の強弱がある。
- ステージ、ラウンド、対戦相手、ボスの進行に伴い、背景だけでなく攻略、空間、テンポ、演出が変わり、終盤ほど大きな驚きへ発展する。
- 限られた色、解像感、スプライト的な動き、手描き表現、パララックス、拡大縮小・回転、限定的なポリゴンやプリレンダーなど、1995年前後のアーケード表現として説明できる一貫した美術方針を持つ。ただし当時の実機性能を厳密にエミュレートする必要はない。
- 短いループでも記憶に残る旋律、操作と同期する効果音、危険・成功・転換を知らせるジングルを持ち、音がゲームの速度と手触りを作る。
- 長い文章、設定画面、保存機能、公開品質ではなく、プレイ画面そのものが作品の魅力を伝える。

M0で`experience-quality.md`へ、参照する時代のジャンル文法、画面方式、キャラクターと背景、アニメーション、音、現代化する点、意図的に採用しない筐体要素を記録する。M2、M4、M5では代表画像と動作中の観察を使い、単にレトロ風のフォントや低解像度を置いただけでなく、遊びと演出が1995年前後のアーケード新作として説得力を持つか比較する。

### 企画選定で確認するアーケード性

企画書に「アーケード風」と書くことや、スコア、残機、ラウンド、少数入力を置くことは根拠にならない。各候補は実装前に、次を具体的なプレイ場面として説明する。

- **10秒の快感**: 説明を読まなくても試せる主要入力と、その直後に返る移動、攻撃、衝突、破壊、回避、獲得などの気持ちよさ。
- **90秒の起伏**: 導入、最初の成功、危険の増加、小さな山場までに、画面、音、判断、テンポがどう変化するか。
- **プレイヤー幻想**: プレイヤーは何者で、何を自在にできるようになり、画面上でどんな格好よさや強さを演じるのか。
- **観戦可能な見せ場**: ルールを知らない人にも、危機、技巧、大成功、敗北の瞬間が動きと音で伝わるか。
- **三つの大転換**: 本編の序盤、中盤、終盤で、空間、目的、操作の意味、攻略、敵との関係の何が大きく変わるか。
- **ボスの約束**: 通常戦の大型・高耐久版ではなく、画面構造と攻略をどう変え、どんな登場と決着を見せるか。
- **再挑戦の差**: 上達、得点、ルート、キャラクター、技、難易度、対戦、生成性など、二回目に異なる判断や表現が生まれる理由。

次の候補は、独自性や実装容易性が高くても採用しない。

- 面白さが説明文や特殊規則の理解後にしか始まらず、主要入力そのものの反応が弱い。
- 全編が同じ空間、同じ目的、同じ基本行為で、敵の反応条件、速度、色、組み合わせだけを増やして発展させる。
- キャラクターや行為の魅力がなく、抽象図形とUIだけで規則を処理することが中心になる。ただし抽象表現自体が強い運動、変形、連鎖、破壊の見せ場を持つ場合は除く。
- スコア、波数、短時間セッション、低解像度、レトロ風表示を除くと、1995年前後のアーケードゲームとしての魅力を説明できない。
- ボス、終盤、別ステージを、通常ループの高耐久化や複雑化だけで作る計画になっている。

企画の採否は機能数の採点合計だけで決めない。致命的な弱点を平均点で隠さず、10秒の快感、プレイヤー幻想、三つの大転換、ボスの約束のいずれかを具体化できない候補は失格とする。

## 更新可能な品質基準

現在の総合基準作品は`ver04.2`とする。これは最初の基準であって固定された上限ではない。M6の比較で新しい完成版が総合的に上回ったことを証明できた場合は、この節の総合基準作品をその版へ更新し、以後は新しい基準を使う。

制作工程の基準は次のとおりとする。

- **公開・配布追跡: `ver13.2`**。状態注入なしの新規Chrome全編、公開commit、配布物hash、14経路、旧版URL、asset MIME、本番runtimeまで追跡した。これは公開検証の手本であり、ゲーム内容、アート、演出、商品性の部門別基準ではない。筐体フローや監査項目の多さを完成度へ加点しない。

基準作品の内容、コード、素材、ジャンルを参照元や土台にはしない。比較するのは、次のような到達水準と制作証拠である。

- 約20分前後を通して中核メカニクスが導入、発展、組み合わせ、最終試験まで変化する製品密度
- 複数の固有環境、攻略対象、山場、最終局面を持ち、一つの短い仕掛けの反復で終わらないキャンペーン
- 背景、主要キャラクター、目標、危険、UI、エフェクト、音楽、効果音が同じ表現方針で作られた完成画面
- 操作の重さ、速度、命中、破壊、回収、選択、成功、失敗が、動きと音によって明確に異なる完成した手触り
- 区間名や敵構成を隠しても、空間、目的、攻略、テンポ、演出から別の局面だと分かる体感上の変化
- 初回導線、難易度差、失敗後の復帰、成長または習熟、設定、保存、ポーズ、結果、終演までつながる製品性
- 多数seedの通し、主要分岐と失敗経路、性能、音量、保存、アクセシビリティ、全主要画面の目視を含む検証深度
- 配布物の生成だけでなく、公開先での起動、版表示、主要経路、旧版保持まで確認したリリース品質

新作が短編に適したジャンルであっても、単純にプレイ時間を水増ししない。その代わり、ルールの組み合わせ、複数の有効戦略、再挑戦価値、物語分岐、生成性などにより、現行基準と比較できる体験の厚みを設計する。ファイル数、コード量、素材数だけを完成度の代理にしてはならない。

新作が一部の評価軸で最高水準に達したが、総合的には現行基準を置き換えない場合、その版を「アート」「初回導線」「戦略性」「アクセシビリティ」などの部門別基準としてこの節へ追記できる。次作は総合基準を下回らないことに加え、関連する部門別基準も比較対象にする。

## 新メジャーバージョンの始め方

まだ作業中の版がなければ、最初の実行で次の順に着手する。

1. 互いにジャンルと遊びが異なる企画を3案以上出す。
2. 各案について、一文の売り、10秒の快感、90秒の起伏、プレイヤー幻想、三つの大転換、ボスの約束、再挑戦の差、代表画面の簡易構図、動きと音の主役を同じ書式で記す。ステージ数や機能一覧だけの案は比較へ進めない。
3. 各案を、独自の楽しさ、操作の手触り、1995年前後のアーケードゲームとしての説得力、視覚・音響の魅力、進行に伴う体感変化、終盤への発展余地、再挑戦する価値、実現可能性、検証しやすさで比較する。「企画選定で確認するアーケード性」の失格条件を先に適用し、致命的な弱点を総合点で相殺しない。
4. 上位2案は、開始、主要入力、最初の成功、危機、小さな山場を示す5場面の絵コンテまたは動作仕様へ落とす。二案の画面が抽象UIや同じ構図へ収束する場合は、採用前に企画を作り直す。
5. 最も強い1案をAI自身が暫定採用し、一文で説明できる中核体験、プレイヤー幻想、完成時の代表場面、作らないもの、M1で不合格なら企画へ戻る条件を定める。
6. 現行の総合基準以上の厚みへ到達するため、初見の発見時間と習熟後の一周時間を分けた想定プレイ時間、固有コンテンツ、メカニクスの発展段階、三つの大転換、山場、ボス、表現、音、検証、公開までを「製品規模契約」として固定する。総合基準より短い場合は、時間差を補う戦略、生成性、分岐、反復差などを受入IDと検証方法へ割り当てる。実装都合だけで後から縮小しない。
7. 新しい`verNN/`を作り、製品設計、ゲーム設計、アート・音響方針、技術設計、品質計画、`status.md`、`log.md`を置く。
8. 文書だけで採用を確定せず、10秒の快感と90秒の起伏を最短で検証するプレイ可能なM1縦切りへ進む。主要入力が気持ちよくない、プレイヤー幻想が画面に現れない、完成表現へ伸ばせない場合は、機能追加で延命せずM0の候補比較へ戻る。

ゲームはPC版Chromeで直接遊べるブラウザゲームを基本とする。ジャンルに適するなら、アクション、パズル、戦略、探索、リズム、シミュレーション、物語ゲーム、またはそれらの融合を自由に選べる。キーボードを必須入力とし、必要に応じてマウス、ゲームパッド、タッチにも対応する。

## 各版に必要な状態管理

ディレクトリ構成は企画に合わせて決めてよいが、現在版には最低限次を置く。

```text
verNN[.x]/
  README.md
  docs/
    00-product-brief.md
    01-game-design.md
    02-art-and-audio-direction.md
    03-technical-design.md
    04-quality-plan.md
    05-major-retrospective.md  # メジャー終了時に作成
    acceptance-matrix.md
    agent-history.md
    experience-quality.md
    asset-inventory.md
    decisions.md
    status.md
    log.md
  game/
```

- `README.md`: 作品名、中核体験、起動方法、現在地。
- `00-product-brief.md`: M0の全候補を同じ書式で比較し、失格条件、上位2案の5場面、採用理由、M1撤退条件、製品規模契約を残す。採用案だけを書いて比較過程を消さない。
- `status.md`: 唯一の正とする進捗、完成条件、証拠、未解決課題、次の最優先作業。
- `log.md`: 日付順の判断、変更、失敗、検証結果。
- `05-major-retrospective.md`: 最終版と過去の基準作品を比較し、作品と自律開発ループの両方を評価したメジャー終了報告。
- `acceptance-matrix.md`: 製品規模契約と完成ゲートの全項目を、実装、テスト、実操作、画面・音、配布物、公開URLへ対応付ける追跡表。
- `agent-history.md`: 各自律実行を起動したエージェントとスクリプト、作業、検証結果、コミット件名を追跡する。
- `experience-quality.md`: 作品の売り、操作の手触り、1995年前後のアーケードゲームとしての表現方針、画面と音の商品性、区間ごとの体感差、山場、終盤、再挑戦理由を定義し、実プレイと動作中の比較で監査する。
- `asset-inventory.md`: 背景、キャラクター、UI、エフェクト、音楽、効果音について、用途、制作方法、権利、完成状態、ゲーム内確認先を管理する。
- `decisions.md`: 重要な選択、比較した代替案、採用理由、予想した効果、後の検証結果を残す。
- 設計文書: 固定仕様ではなく、プレイ検証で更新する仮説。要件を変えた理由を記録する。

`acceptance-matrix.md`の各行には安定したIDを付ける。チェックだけで完了にせず、証拠ファイルまたは再実行可能なコマンドを記載する。MVPや途中マイルストーンで延期した製品要件は削除せず、担当段階を明記する。

## 実行エージェントの来歴

`run-codex-loop.sh`と`run-claude-loop.sh`は、次の環境変数を各実行へ渡す。

- `SHOOT_MATA_AGENT_LOOP`: `codex`または`claude`
- `SHOOT_MATA_AGENT_SCRIPT`: 起動したシェルスクリプト名
- `SHOOT_MATA_AGENT_RUN_NUMBER`: そのループ内の実行番号
- `SHOOT_MATA_AGENT_RUN_STARTED_AT`: 実行開始時刻

各実行は対象版の`docs/agent-history.md`へ次の形式で1行を追加し、同じ内容の要約を`docs/log.md`にも残す。

```md
| 開始時刻 | Agent | Script | Run | 作業・結果 | 検証 | Commit subject |
| --- | --- | --- | ---: | --- | --- | --- |
| 2026-11-06T20:00:00+0900 | Codex | run-codex-loop.sh | 3 | Stage 2を実装 | verify合格 | feat(ver12): add stage 2 |
```

各コミット本文の末尾には、実行元を機械的に検索できるよう次のtrailerを付ける。

```text
Agent-Loop: codex
Agent-Script: run-codex-loop.sh
```

Claudeの場合は`claude`と`run-claude-loop.sh`を使う。一つの実行で複数コミットを作る場合はすべてに付ける。環境変数がない対話実行では、スクリプトを推測せず`Agent-Loop: interactive`、`Agent-Script: none`と記録する。追跡導入前の過去版や過去コミットも、確実な証拠がなければ推測で埋めず`unknown`とする。

開発段階は原則として次の順に進める。

| 段階 | 目的 | 次へ進む条件 |
| --- | --- | --- |
| M0 企画・規模契約 | 白紙企画、対象体験、製品規模、完成表現、非目標を決める | 3案以上に10秒の快感、90秒の起伏、プレイヤー幻想、三つの大転換、ボスの約束、再挑戦の差があり、失格条件を通過した上位2案を5場面へ具体化している。採用案では現行基準との差、手触り、1995年前後のアーケード表現、M1撤退条件、検証方法が受入追跡表へ割り当てられ、数や機能だけを代理指標にしていない |
| M1 中核縦切り | 最小構成で独自の面白さと基本動作の気持ちよさを証明する | 10秒の主要入力と90秒の起伏を実操作で確認し、判断、失敗、上達が発生する。成功・失敗の視覚・音響フィードバック、プレイヤー幻想、観戦可能な見せ場が試作品の言い訳なしに比較できる。中核が面白くない、説明を読まないと始まらない、または完成表現へ伸ばせない場合は企画を再選定する |
| M2 製品基盤 | 導入、設定、復帰と、完成画面・動き・音の制作規格を確立する | 仮素材なしの代表区間が、静止画だけでなく実プレイ中のキャラクター性、奥行き、動き、衝突、成功演出まで現行基準と比較できる品質になる |
| M3 本編制作 | 固有コンテンツとメカニクスを段階的に発展させる | 規模契約を削らず開始から終演まで到達でき、初見相当と習熟済みの両ペースを計測して想定下限を大きく割っていない。主要区間の空間、目的、操作、攻略、テンポ、見せ場を比較し、名称、色、数値、敵構成だけの違いを固有コンテンツへ数えていない。現行総合基準との差も同一軸で仮比較し、不足をM4へ延期せず本編の内容か深さとして追加する |
| M4 深度・表現拡張 | 単調さを除き、攻略、手触り、演出、音、山場、再挑戦価値を深める | 区間名や色を隠しても各区間の空間・目的・攻略・テンポ・見せ場を判別でき、通常区間、ボス、終盤が動作中にも別の体験となり、短い試作感や素材不足がなくなる |
| M5 批評・改善・公開 | 原則2回以上のマイナー改善と製品監査を行う | 動作中の商品性、手触り、体感差、ボス、終盤を含む比較批評と完成ゲートに合格し、公開確認、旧版保持確認まで完了する。数、フロー、監査の充実だけで重大な表現不足を合格にしない |
| M6 メジャー振り返り | 作品と自律開発ループを比較評価し、ルート方針を改善する | 振り返り、README改善、最終コミットが完了する |

## 1回の自律実行プロトコル

1. **復元**: ルートREADME、現在版のREADME・`status.md`・最新ログ、`agent-history.md`、git状態を読む。`SHOOT_MATA_AGENT_*`から今回の実行元を確定し、中断中の変更を重複させない。
2. **選択**: 現在のM0〜M6、未達の完成条件、製品規模契約、実際のプレイ品質から、体験への効果が最大の課題を1つ選ぶ。安全に実装できることを質問に置き換えない。
3. **制作**: 動作する縦切りとしてコード、データ、素材、テストを更新する。不具合修正には可能な限り回帰テストを付ける。
4. **体験**: 実際にブラウザで遊び、主要操作の反応、通常区間、山場、終盤を動作中に観察する。代表画像に加えて、入力前後や命中・失敗・転換の連続フレームまたは短い記録を比較し、静止画と数値だけで面白さ、手触り、見栄えを判定しない。自動操縦は到達性の補助であり、プレイ批評の代替にしない。
5. **検証**: 関連テスト、ビルド、通しプレイ、性能、音量、保存、入力を変更リスクに応じて確認する。重大な欠陥は同じ実行内で直して再検証する。
6. **記録**: `status.md`、`log.md`、`agent-history.md`、受入追跡表へ、実行元、結果、証拠、残課題、仕様差、次に行う具体的な1作業を残す。段階を終える場合は、目的、変更ファイル、完了事項、検証結果、未確認事項、仕様変更と理由、次作業を短い完了報告として残す。
7. **保存**: 検証済みの意味ある単位を、実行元trailer付きでコミットする。公開設定が整っている場合は、完成ゲートを通った版だけを公開し公開物も確認する。

調査や計画だけが必要な段階を除き、1回を文書更新だけで終えない。反対に、未検証の大量実装を「完成」と記録しない。ユーザーの未コミット変更は保持し、無関係な変更を混ぜない。

## 制作で活用するノウハウ

- 最初の数十秒で中核の面白さを操作として伝え、説明文に依存しない。
- 入力には即時の視覚・音響フィードバックを返す。
- 主要操作ごとに、予備動作、実行、接触、結果、回復の時間設計を調整する。エフェクト数ではなく、重さ、速度、距離、停止、反動、音の立上がりから手触りを批評する。
- 新要素は単独で理解させ、組み合わせで応用させ、終盤で習熟を試す。
- 初見の探索時間だけで製品規模を満たしたと判断しない。既知解または習熟方針の実測が想定下限を大きく割る場合、得点肩書や待ち時間だけで埋めず、固有判断、組み合わせ、山場、別戦略の密度をM3中に増やす。
- 難しさを体力や物量だけで作らず、予告、位置取り、優先順位、リスクと報酬で攻略を作る。
- ゲーム規則と描画を分離し、固定時間刻みと決定的入力で高速・再現可能に検証する。
- ステージ、レベル、敵、会話などは可能な範囲でデータ駆動にする。
- 自動テストと自動操縦は到達性、回帰、所要時間、密度の検査に使い、人間相当の画面評価とプレイ批評を併用する。
- ブラウザ監査は一意ポートまたは明示した対象URLで起動し、作品名と版を開始時にassertする。残存サーバーや別版へ接続した結果を採用しない。
- 初見検証は新規保存、状態注入なし、攻略専用ショートカットなしで開始する。開発者が正解を知る自動通しだけを、理解しやすさの証拠にしない。
- 外部プレイヤーを利用できない場合も改善を止めず、初見相当の入力制限、複数の自動方針、失敗ログ、無操作・誤操作、異なるseedによる代替実験を設計する。測れない主観は未確認と明記する。
- ジャンルが許す限り、少なくとも複数の有効戦略、解法、構成、難易度またはプレイ方針を比較する。一つの固定解を自動操縦が成功しただけで、深さや再挑戦価値を合格にしない。
- 仮素材は試作中だけ許可し、完成版からデバッグ表示、無意味な代用図形、未調整素材を除く。
- 単純なCanvas図形だけで全編を済ませる場合も、それが意図した完成表現であることを画面比較で証明する。制作の速さを理由に、背景、キャラクター、動き、エフェクト、音の固有性を省略しない。
- ステージ数、波数、敵数を増やす前に、既存区間を名前、色、数値、敵配置から独立して比較する。同じ空間で同じ入力と同じ目的を繰り返す区間は、敵の組み合わせや文章が違っても体感上は一つとして扱う。
- ボスは大型表示や高耐久だけで完成扱いにせず、登場、専用行動、空間への干渉、攻略転換、撃破の各局面で通常戦にない体験を作る。
- 画面の豪華さだけで完成度を判定せず、主役、目標、危険、操作結果の視線誘導を守る。一方、読みやすさだけを理由に造形、素材感、背景、アニメーションを省略しない。
- アクセシビリティ、ポーズ、再開、保存、音量設定、初回説明、失敗後の復帰を製品の一部として扱う。
- `npm run verify`など、ビルド・テスト・監査をまとめて再実行できる入口を用意する。

## メジャー版の完成ゲート

企画時にジャンル固有の基準を追加し、少なくとも以下をすべて満たした場合だけ完成とする。最初の通し成功、6区間の実装、配布物生成、テスト全件合格のいずれか一つだけで完成としてはならない。

- タイトルから主要な終着点まで、通常操作と自動検証の両方で到達できる。
- タイトルまたは起動から開始、プレイ、失敗、再挑戦、主要な終着点まで、企画に必要な製品フローが途切れず、不要な儀式や長い説明を挟まない。
- 企画に適した入力方式で開始でき、主要操作、目的、危険、成功、失敗をプレイ中の反応から理解できる。
- 対象とする最小画面と標準画面で全主要場面を確認し、UIの正常表示だけでなく、主役、世界、目標、危険、エフェクトが一つの完成画面として成立する。
- 1995年前後のアーケードゲームとして、ジャンルの即時性、強いシルエット、誇張された動き、局面ごとの見せ場、音による手触りが一貫している。筐体フローの有無やレトロ風の装飾だけで合格にしていない。
- 習熟済みの実測時間、最初の操作と数分間、難易度曲線、失敗後の復帰、最後まで遊ぶ動機、再挑戦動機を検証している。
- 最初の10秒で主要入力自体の気持ちよさが伝わり、最初の90秒に成功、危機、テンポまたは画面の変化、小さな山場がある。説明文を理解したことだけを初回体験の成功にしていない。
- 中核メカニクスが複数の意味ある判断と有効戦略を生み、導入、発展、組み合わせ、最終試験の4段階以上で変化する。
- 操作、ルール、危険、目的、結果がプレイ中に理解できる。
- 主要コンテンツに固有の環境、判断、攻略、見せ場があり、座標や速度だけを変えた反復や量だけの水増しになっていない。
- 少なくとも二つの大きな山場と、既習要素を再構成する最終局面がある。
- 主要区間を名前、色、文章、敵構成の情報なしで比較しても、空間、目的、操作の意味、攻略、テンポ、演出の差を説明できる。同じ舞台と同じ行為の反復を固有区間数へ水増ししていない。
- 主役と主要な敵・対象に、機能的識別を超えた造形、動き、反応があり、作品を記憶する視覚的な焦点がある。
- 移動、主要アクション、命中または成功、被害または失敗、撃破または完了に、動きと音の強弱があり、入力前後の連続観察で手触りを説明できる。
- ボスと終盤が通常区間の高耐久版に留まらず、画面、規則、攻略、演出の少なくとも二つを大きく変える。
- 初見プレイ、慣れたプレイ、異なる戦略または難易度で、体験や判断に意味のある差が生じる。
- 新規制作した背景、主要キャラクター、UI、エフェクト、音楽、効果音が一貫した方向性を持ち、仮素材や無音の主要場面が残っていない。
- 最初の数分、通常区間、全固有環境、全山場、最終局面、結果、終演を画像として採取し、主要操作、衝突、成功、失敗、局面転換は連続フレームまたは短い動作記録でも比較している。
- 単体・統合・通しテストに加え、複数seedまたは複数戦略の反復、代表的な性能・音量計測、保存破損、失敗・再挑戦・ポーズ・復帰を検証している。
- クラッシュ、進行不能、入力不能、保存破損、重大な音量・視認性問題がない。
- 原則2回以上の独立した自己批評で、初回理解だけでなく、深さ、テンポ、戦略、演出、音、終盤の満足度を実際に改善している。
- 現行の総合基準・関連する部門別基準と最終候補を同じ評価軸で比較し、規模が小さい場合は別の深さで同等以上の価値があると証拠付きで説明できる。テスト件数、機能数、フロー、ファイル数、素材数、公開経路数だけを優位性の根拠にしない。
- 「知らない人へ一本だけ勧めるならどちらか」「短い紹介を見てどちらを遊びたいか」「最後まで遊んだときどちらが記憶に残るか」を現行基準と比較し、最終候補を選べない重大な弱点が残る場合は完成にしない。
- 最終配布物を公開し、公開URLの起動、版表示、主要経路、旧版URLを確認している。権限不足時は未公開を完成とせず、阻害要因として残す。
- 受入追跡表の全必須IDが、実装、再実行可能な検証、目視または聴覚の代替証拠、最終配布物へ結び付いている。
- クリーン環境で依存関係を固定してbuildとverifyを再実行し、ローカルの古い`dist`や証拠ファイルへ暗黙依存していない。
- 配布物のファイル一覧とハッシュを記録し、検証した候補と公開物が一致する。旧版保持とrollback方法も確認する。
- 起動方法、操作、検証結果、既知の制約が文書化されている。

完成状態は次の語を区別する。

- **Prototype**: 中核仮説だけを試せる。製品完成ではない。
- **Vertical Slice**: 代表区間が完成品質。残りの本編は未完成。
- **Content Complete**: 規模契約の本編と素材が揃ったが、横断調整と最終監査前。
- **Release Candidate**: 完成ゲートをローカルで通った公開候補。未公開なら製品完成ではない。
- **Published Product**: 候補と同一の公開物を実URLで確認済み。
- **Major Closed**: 原則2回以上の改善、公開、M6振り返り、ルートREADME改善まで完了。次メジャーへ進める唯一の状態。

## マイナー版と次の新作

`verNN.0`の本編がつながったら、少なくとも一度は体系的に自己批評する。最初の数分、テンポ、反復、選択の偏り、理解しにくさ、攻略の単調さ、画面の商品性、キャラクターの魅力、音と手触り、局面変化、ボス、終盤の満足度を証拠とともに評価する。

直前版を新しい`verNN.x/`へ複製し、証拠上の効果が高い3〜5件へ絞って改善する。原則として、最初のマイナー版では理解、操作、視認性、テンポ、基本手触りを、次のマイナー版では戦略の深さ、体感上のコンテンツ差、キャラクターと背景、動き、音、ボス、終盤、再挑戦価値を批評する。二回目を得点規則や説明追加だけで終えず、完成画面と動作中の印象を必ず対象にする。問題がなかったという結論も、通し、連続した動作観察、画像、計測、比較を伴わなければ改善回数に数えない。

各マイナー版の開始前に、直前版の通し時間、成功・失敗、選択率、主要画面、性能、音量、テスト、既知課題をbaselineとして固定し、改善後も維持すべき品質を「非退行条件」として列挙する。新しい改善が既存の長所を壊した場合は完了せず、修正または明示的な優位性の比較まで行う。

実装が難しい、予定より大きい、テストが通った、6区間作った、配布物が小さい、次の企画を思いついた、という理由で改善を打ち切らない。残る課題が好みの範囲に限定され、完成ゲートと現行基準との比較に合格して初めてM5を終了する。

## M6 メジャー終了時の振り返りとループ改善

最終マイナー版の公開確認後、次のメジャー版を作る前に必ず独立した1回以上の実行をM6へ使う。実装を追加する回ではなく、完成作品と自律開発の方法を監査し、次の制作能力を高める回とする。

1. 最終版、現行の総合基準作品、関連する部門別基準、直近2つのメジャー完成版を、製品規模、中核の独自性、基本操作の手触り、判断の深さ、体感上のコンテンツ差、最初の数分、テンポ、キャラクター、アート、動き、音、演出、ボス、終盤、再挑戦価値、1995年前後のアーケードゲームとしての説得力、アクセシビリティ、検証深度、公開品質で比較する。筐体フローは企画が採用した場合だけ評価し、完成度の共通加点にはしない。`ver04.2`が総合基準でなくなった後も、初期アンカーとして必要に応じて比較へ残す。
2. 「よかった点」「現行基準を超えた点」「現行基準より後退した点」「小さく安全にまとめすぎた点」「数やフローで過大評価した点」「自動テストでは見逃した点」を、画像、動作中の観察、計測、通し結果、実装事実と結び付ける。
3. 企画選定、規模契約、マイルストーン、完成ゲート、批評方法、テスト、素材制作、公開のどこが結果を生んだかを原因まで掘り下げる。完成版の弱点をM0の失格条件で予見できたか、上位2案の5場面比較とM1撤退条件が実際に機能したかも監査する。
4. 新作が現行基準を総合的に上回り、製品性、検証、公開品質に重大な後退がない場合は、この節の総合基準作品を新作の最終版へ更新する。特定軸だけを明確に上回った場合は部門別基準へ追加する。昇格理由と比較証拠を振り返り文書へ残す。
5. 再発しうる問題と再利用できる成功だけを一般化し、ルート`README.md`の指示、基準作品、段階、チェック項目を実際に更新する。作品固有の設定や数値は持ち込まない。
6. 完成版の`docs/05-major-retrospective.md`、`status.md`、`log.md`へ比較結果、基準の昇格判断、README変更内容、変更理由を記録する。READMEを変えない場合も、現行ループと基準で十分な理由を証拠付きで残す。
7. ルートREADME、振り返り文書、状態記録を検証して一つの明確なコミットにする。そのコミット後だけ`ver(NN+1)/`を開始できる。

M6でREADMEを更新することは、過去作品のコードや素材を次作へ流用することではない。制作方法を経験から改善するための必須工程である。README変更によって現在の自律ループが自分自身を際限なく緩和しないよう、完成ゲートの削除や縮小には、それ以上に厳密でジャンルに適した代替基準と比較証拠を必須とする。

## ループの実行

CodexまたはClaude Codeを使い、既定で12回、30分間隔で進める。

```sh
./run-codex-loop.sh [run-count] [wait-minutes]
./run-claude-loop.sh [run-count] [wait-minutes]
```

例: `./run-codex-loop.sh 5 10`。各回は独立したエージェント実行で、失敗時は後続を止める。引数と環境は`--help`で確認できる。

## AIが止まってよい条件

通常の企画、命名、技術選定、素材方針、難易度調整、批評、次版への移行判断では止まらない。必要な認証・権限がない、ユーザー変更と安全に分離できない、回復困難な外部操作が必要、または外部障害が続きローカル作業も尽きた場合だけ、阻害要因と再開条件を具体的に報告する。
