# shoot-mata v4 自律開発計画

このリポジトリでは、AIエージェントが人間の追加設計や承認を待たず、オリジナルのブラウザ向け横スクロールシューティングを企画、実装、検証、評価、改善、公開する。

ユーザーが繰り返し入力する指示は、原則として次の一文だけでよい。

> README.md および各種ドキュメントに沿って開発を進めて

AIはこの指示を受けるたび、下記の状態管理と優先順位に従い、未完了の作業を自分で選んで前進させる。設計判断、素材方針、難易度調整、画面評価、バージョンアップ判断のために人間へ指示を求めない。

## 現在地

- v1〜v3.4は完成済みの過去版として保持する。既存ディレクトリを変更、削除、移動しない。
- 現在公開中の最新版はv3.4であり、v4.0が公開基準を満たすまでは公開トップを切り替えない。
- v4系は`ver04/`から新設する。現時点では本READMEによる開発計画の策定が完了し、次回の指示からv4.0の事前設計を始める。
- v4.0完成後はAI自身が問題を抽出し、v4.0を保持したまま`ver04.1/`、続いて`ver04.2/`を作る。

## v4の絶対原則

### 完全新作とする

v4はv3の大型改修ではない。次のものをv1〜v3系からコピー、移植、流用しない。

- 背景、プレイヤー、敵、ボス、アイテム、エフェクト、UIなどの画像素材
- BGM、効果音、音声素材
- 世界観、固有名詞、シナリオ、ステージ案、敵案、ボス案
- 武器、OPTION、リアクター、パワーアップ、残機復帰などのゲームシステム
- ステージデータ、敵出現表、数値バランス、画面レイアウト
- v3のゲームコードを複製して名前や定数だけを変更すること

過去版から利用してよいのは、以下の方法論と一般的な知見だけとする。

- 固定時間刻みによる再現可能なゲーム進行
- ゲーム規則とブラウザ描画の分離
- データ駆動のステージ構成
- 単体テスト、自動操縦、Chrome通しテスト
- スクリーンショットをAI自身が目視する画面品質確認
- 音量、密度、所要時間、性能を数値で検査する考え方
- 合格したビルドだけをGitHub Pagesへ公開するCI
- 旧版を固定URLで保持し、新版を別ディレクトリで作る運用

v4の初期実装は空の`ver04/`から始める。過去版のソースを土台にせず、設計書で決めたゲームに必要な最小構成を新規に作る。技術的に一般的な小さな処理を同じ考え方で再実装することはよいが、過去版のファイル単位のコピーは禁止する。

### プレイヤー体験を最優先する

- 文書を増やすことではなく、操作して面白いゲームを作ることを目的とする。
- 実装量や敵数だけで完成と判定しない。テンポ、判断、駆け引き、発見、上達、演出のまとまりを評価する。
- ストーリーは説明文ではなく、背景変化、地形、敵の行動、目的、音、ボス攻略を通じて体験させる。
- 敵とボスは耐久力だけで難しくしない。位置取り、優先順位、攻撃予告、弱点、リスクと報酬で攻略を作る。
- 新要素は単独で理解させ、組み合わせで応用させ、ステージ終盤で習熟を試す。

### 人間の確認を待たない

- 通常の企画、命名、技術選定、アート方針、難易度調整、バグ修正はAIが決める。
- 選択肢をユーザーへ提示して止まらない。複数案がある場合は、評価軸を定めて最善案を選び、理由を記録する。
- 作業中に失敗しても、安全な代替手段を試す。失敗と解決は作業記録へ残す。
- 認証情報が必要、権限がない、回復困難な外部操作が必要など、AIだけでは安全に解決できない場合のみ具体的な阻害要因を報告する。

## v4.0の製品目標

ゲームの具体的な世界観と中核システムは、v4.0のM0で複数案を比較して決定する。ただし、完成版は以下をすべて満たす。

1. 独自性
   - 一文で説明できる独自の中核メカニクスを持つ。
   - 攻撃、移動、防御、強化の少なくとも3つが中核メカニクスと相互作用する。
   - 過去版や既存商用作品の名称、キャラクター、画面、ステージ、音を複製しない。
2. キャンペーン
   - 6ステージ以上と最終ボス、エンディングを持つ。
   - 1周15〜25分を目安とし、長さではなく密度を優先する。
   - 全ステージで、舞台、遊びのルール、敵編成、山場、ボス攻略が異なる。
3. 戦闘
   - 通常敵24種以上、ボス6種以上を用意する。
   - 小型、大型、固定、支援、妨害、奇襲などの役割を明確に分ける。
   - 敵弾、体当たり、地形、目的物の危険が視覚的に判別できる。
4. 成長
   - v3のリアクター、3色コア、OPTIONとは異なる新しい強化システムを設計する。
   - 強化は単純な火力上昇だけでなく、プレイ方針が変わる選択を含む。
   - 初期状態やミス後にも勝機があり、強化状態では別の判断が生まれる。
5. 操作
   - キーボードで直感的に遊べ、最低2つのアクション入力を使い分ける。
   - 入力には常に即時の視覚・音響フィードバックがある。
   - 画面端、復帰、ポーズ、コンティニューで操作不能や詰みが起きない。
6. 表現
   - v4専用に作った背景、キャラクター、敵、ボス、UI、エフェクト、音だけを使う。
   - 仮素材は開発中だけ許可し、v4.0公開時には残さない。
   - 各面の配色だけでなく、形、奥行き、動き、光、天候・環境現象を変える。
7. 製品性
   - タイトル、操作説明、設定、ポーズ、結果、コンティニュー、エンディングをつなぐ。
   - BGMと効果音を個別調整でき、音量監査に合格する。
   - PC版Chromeで安定して動作し、60fps相当の処理余裕を持つ。

必須要件はAIの都合で縮小、削除、延期しない。要件を変更できるのはユーザーが明示した場合だけとする。

## リポジトリ構成

v4.0着手時に次の構成を新規作成する。

```text
ver04/
  README.md
  docs/
    00-product-brief.md
    01-game-design.md
    02-art-and-audio-direction.md
    03-technical-design.md
    04-quality-plan.md
    status.md
    log.md
  game/
    assets/
    src/
    tests/
    scripts/
```

- `00-product-brief.md`: 複数の企画案、比較、採用案、独自性、対象体験、非目標。
- `01-game-design.md`: 操作、中核ループ、強化、全ステージ、敵、ボス、難易度、画面遷移。
- `02-art-and-audio-direction.md`: v4専用の造形言語、色、光、素材、UI、エフェクト、音楽、効果音、素材台帳。
- `03-technical-design.md`: 実行構成、状態管理、描画、衝突、保存、ビルド、公開。
- `04-quality-plan.md`: 自動テスト、画面検査、音量、性能、完成判定。
- `status.md`: 現在版、マイルストーン、直近の達成内容、未解決課題、次の最優先作業を一か所に記録する。
- `log.md`: 日付順の短い作業記録。結果、失敗、判断、検証値を残す。

v4.1では`ver04.1/`、v4.2では`ver04.2/`を新設し、それぞれに改善方針書`docs/00-v4.x-direction.md`を実装前に作る。直前版は変更しない。

## 自律実行プロトコル

ユーザーから「README.md および各種ドキュメントに沿って開発を進めて」と指示されたら、AIは毎回、次を順番に実行する。

1. 状態を復元する
   - ルートREADME、対象版README、`docs/status.md`、最新の`docs/log.md`、git状態を読む。
   - 前回が中断していた場合は、部分変更と実行中プロセスを調べ、重複実装せず安全に再開する。
   - 過去版ではなく、`status.md`が示す現在版だけを編集対象にする。
2. 次の作業を決める
   - 現在マイルストーンの未達条件から、プレイ体験への影響が最大の課題を1つ選ぶ。
   - 依存関係がある場合は、その課題を完了可能な最小の縦切りへ分解する。
   - 「調査だけ」「計画だけ」で終えず、その回で安全に実装できるものは実装する。ただし現在マイルストーンが設計の場合は、設計の完成を作業成果とする。
3. 実装する
   - 動作する単位でコード、データ、素材、テストを更新する。
   - 不具合修正には、同じ不具合を再現する回帰テストを追加する。
   - 仮素材を使った場合は台帳と`status.md`へ残し、公開前に必ず置換する。
4. 自分で評価する
   - 関連する単体テストを実行する。
   - 画面や演出を変えたらChromeで実行し、スクリーンショットをAI自身が画像として確認する。
   - ゲームバランスを変えたら、自動操縦の所要tick、被弾、敵密度、攻略進行を確認する。
   - 音を変えたら音量監査、負荷を増やしたら性能計測を行う。
5. 仕上げる
   - 発見した重大な欠陥は同じ回で修正して再検証する。
   - `status.md`と`log.md`を更新し、次回の最優先作業を具体的に一つ残す。
   - 検証済みのまとまりをコミットする。安全な区切りでは`main`へpushする。
6. 公開を扱う
   - 公開対象の完成条件を満たした版だけ、CIを通してGitHub Pagesへ公開する。
   - Actionsの成功だけで終わらず、公開URL、版表示、旧版URLのHTTP応答を確認する。
   - 公開失敗は放置せず、原因を修正して再検証する。

1回の指示で選ぶ主課題は原則1つだが、その課題を完成させるための実装、テスト、画像確認、文書更新、コミットは同じ回に含める。小さすぎる変更を繰り返して進捗を装わない。

## v4.1・v4.2の自己改善ループ

v4.0公開は終了ではなく、自己改善の開始点とする。ユーザーが同じ指示を繰り返した場合、AIは以下を自動で行う。

### v4.1

1. v4.0を保持し、コード変更前に自動プレイ、全画面画像、所要時間、被弾、武器選択率、敵別撃破時間、ボス形態時間、性能を再収集する。
2. 次の観点でAI自身が批評する。
   - 最初の30秒で面白さが伝わるか
   - 同じ行動の繰り返しや空白時間がないか
   - 強化選択に意味があり、死に選択肢がないか
   - ステージの物語と変化が操作中に伝わるか
   - 敵とボスの攻略が耐久力の差だけになっていないか
   - 画面の美しさと危険の読みやすさが両立しているか
   - 音と演出が操作感を強めているか
3. 影響度、頻度、修正効果、回帰リスクで課題を採点し、上位3〜5件を`ver04.1/docs/00-v4.1-direction.md`へ固定する。
4. `ver04.1/`を新設し、課題の修正、回帰テスト、全通し、画面確認、公開を行う。

### v4.2

1. v4.1を同じ基準で再評価し、v4.1で残った問題と、改善によって新しく生じた問題を分ける。
2. 数値上は正常でも、単調、分かりにくい、驚きがない箇所を重点的に探す。
3. `ver04.2/docs/00-v4.2-direction.md`を実装前に作成し、再び3〜5件へ優先順位を絞る。
4. v4.0とv4.1を保持したまま`ver04.2/`を作り、検証済みの最新版として公開する。

4.1と4.2では機能数を増やすこと自体を目標にしない。削除、短縮、再配置、数値調整、視覚改善も、体験への効果が高ければ主要な改善として扱う。

## 自己評価の必須証拠

AIは「よくなった」という主観だけで完了させず、変更に応じて以下を残す。

- 自動プレイの面別所要tick、被弾、コンティニュー、地形接触
- 敵密度、無戦闘時間、敵種別の出現・撃破・生存時間
- 強化候補の選択率と、構成別の火力・生存・攻略時間
- ボスの形態別時間、弱点成功回数、攻撃別被弾
- 音素材のRMS・ピーク、同時発音、BGMとの相対音量
- 最重負荷場面の平均、p95、最大処理時間
- タイトル、通常戦、セットピース、全ボス、結果、エンディングの画面画像
- 変更前後の差と、改善しなかった点

数値は判断を補助するものであり、面白さの代わりではない。画像と実際のプレイ進行も必ず合わせて評価する。

## 実装・検証・git運用

- 対象環境はPC版Google Chromeとキーボード操作を必須とする。
- ゲーム規則はブラウザ描画から分離し、決定的な入力で高速テストできるようにする。
- `npm run verify`など単一コマンドで、ビルド、単体テスト、音量監査、Chrome通し、性能ゲートを実行できるようにする。
- 素材には用途、版、生成・制作方法を記録し、使用権が不明な外部素材を入れない。
- ユーザーの既存変更を上書きしない。作業開始時にgit状態を確認する。
- 破壊的な操作を避け、旧版を変更しない。各版は独立したURLと保存領域を持つ。
- コミットは検証済みの意味ある単位にする。未完成を完成と記録しない。
- `main`へのpush後はCIと公開を監視し、公開物まで確認する。

## AIが止まってよい条件

通常は、同じ指示を受けるたびに次の未完了作業へ進む。次の場合だけ作業を止め、理由と再開条件を明記する。

- 必要な認証や権限がなく、代替手段もない
- ユーザーの未コミット変更と不可避に競合し、安全に分離できない
- 外部サービス障害が複数回続き、ローカルで進められる作業も残っていない
- ユーザーの新しい指示が本READMEの必須要件と明確に矛盾する
- v4.2が公開済みで、v4.0、v4.1、v4.2の完成条件と公開確認がすべて完了している

作業が難しい、時間がかかる、判断が必要という理由では止まらない。安全な範囲で仮説を立て、実装と検証によって判断する。

## 次回の開始作業

次に「README.md および各種ドキュメントに沿って開発を進めて」と指示されたAIは、v4.0のM0を開始する。

1. `ver04/`と上記ドキュメント群を新規作成する。

3. 独自性、操作の深さ、6面への展開力、AIによる実装・検証可能性で比較し、1案を自律的に採用する。
