## 製品目標

90年代アーケードシューティングを思わせる、懐かしくも新しいブラウザ向け横スクロールシューティング。アーケードの1周として遊びごたえのある量と、地形と敵を組み合わせたステージ構成を持たせます。

### 必須要件

1. **ステージ量**
   - 6ステージ以上と最終ボスまでを1周とする。1ステージは3〜5分、1周で25〜35分を目安にする。
   - 各ステージに固有の舞台、地形、敵編成、中ボスまたは山場、ボスを用意する。色や敵の数だけを変えたステージは数えない。
2. **地形**
   - 各ステージに当たり判定のある地形（天井、床、壁、狭い通路、動く地形、壊せる地形など）を置く。地形への接触はミスとし、見た目と当たり判定を一致させる。
   - 地形はステージデータとして定義し、背景の絵とは別レイヤーで描く。地形のない開けた区間も構成の一部として使う。
3. **敵と構成**
   - 通常敵は全体で20種以上。各ステージに初登場の敵を3種以上置く。
   - 地形と組み合わせる敵を必ず含める（床・天井を歩く敵、地形に設置された砲台、ハッチから出る敵、地形に隠れる敵、壁を壊して進む敵など）。
   - 各ステージは「導入 → 展開 → 山場 → ボス」の区間構成を持ち、新しい要素は単独で見せてから組み合わせる。
4. **武器とパワーアップ**
   - 自機は常に基本ショットを撃てる。強化アイテムやコアがゼロでも攻撃不能にはならず、ミス後も基本ショットで立て直せる。
   - 系統の異なる主武器3系統以上、各3段階以上の成長と、選択や組み合わせによる判断を持つ。v02の三連装リアクターを引き継ぐかは `ver03/docs/01-game-design.md` で決める。
5. **画面とUI**
   - プレイ中に常に出ているUI（スコア、残機、武器、ボス体力など）はプレイフィールドの外の帯に置き、自機、敵、弾、地形に重ねない。
   - プレイフィールド内には、ステージ開始・警告・クリアなどの短い演出（1.5秒以内）だけを出す。
   - タイトル、操作説明、ポーズ、設定、結果、コンティニュー、エンディングを1本の流れとしてつなげる。
6. **グラフィック**
   - v02で評価されたグラフィックの質と、背景の多重スクロールを維持する。
   - 背景のループ部分や画像の境目で、つなぎ目が見えないようにする。
7. **音**
   - BGMと効果音を用意し、効果音がBGMを覆い隠さない音量バランスにする（ミキサー、同じ効果音の同時発音数の上限、必要に応じてダッキング）。
   - BGMと効果音の音量は設定で個別に変えられる。
8. **独自性**
   - 他作品のキャラクター、名称、画面、音、素材を複製しない。

これらの要件はAIの判断で縮小・延期しません。変えてよいのはユーザーの明示的な指示があったときだけです。

## 対応環境

- 検証の対象はPCのChrome（デスクトップ、キーボード操作）だけにします。
- Firefox、Edge、Safari、スマートフォン、タッチ操作は、余力があれば対応します。難しければ対応しなくても完成としてよく、READMEの完成判定には含めません。

## 開発プロセス

### 原則

- **人間の確認はしない。** 進行の判断、主観品質の代わりの確認、公開まで、すべてAIが自動検証の結果で決める。ユーザーに承認を求めて止まらない。
- **作るものを優先する。** 文書と監査スクリプトは、ゲームを作るのに必要な最小限にする。証拠の書式や台帳を厚くするために作業時間を使わない。
- **常に遊べる状態を保つ。** `main` の最新コミットは常にビルドと自動テストに通り、Chromeで起動して遊べる状態にする。
- **見た目はAIが自分で見て確かめる。** スクリーンショットを撮って画像として読み、下の「画面チェック項目」に照らして直す。

### 自動検証

- `ver03/game/` で `npm run verify` 1回で、ビルド、ユニットテスト、Chromeでの通しテストまで実行できるようにする。
- Chromeでの確認はPlaywrightなどでスクリプト化し、人が操作しなくても再実行できるようにする。
- 通しテストは決まった入力列か自動操縦で、各ステージを開始からボス撃破・結果まで進める。地形にめり込む、詰む、弾が撃てない状態がないことを確認する。
- 音量バランスは、BGMと効果音の音量（RMSやラウドネス）を数値で測って調整する。

### 画面チェック項目

UIや絵を変えたら、Chromeでスクリーンショットを撮り、AI自身が次を確認します。

- 常時表示のUIがプレイフィールドに重なっていない。
- 背景のループ部分や画像の端に、つなぎ目が見えない（ループ部分を含むスクリーンショットで確認する）。
- 地形の見た目と当たり判定がずれていない（当たり判定を重ねて描くデバッグ表示で確認する）。
- 自機、敵、敵弾、アイテム、地形が背景に埋もれず、見分けられる。
- 仮の図形やデバッグ表示が、通常のプレイ画面に残っていない。

### 公開

- `main` へのpushで、CIが `npm run verify` を通した場合だけ自動でGitHub Pagesへ公開する。手動の確認入力は使わない。
- 公開に失敗したり公開版が壊れていたら、直前のコミットへ戻すか修正をpushして直す。

## AIエージェントの作業手順

ユーザーから「README.md および各種ドキュメントに沿って開発を進めて」と指示されたら、確認を求めずに次の手順で進めます。

1. このREADME、`ver03/docs/`、`ver03/docs/log.md` の最後の記録、git状態を読む。
2. 現在のマイルストーンで、まだできていない一番大事なことを選ぶ。前回終わった作業は繰り返さない。
3. 動く単位で実装し、テストと画面チェックを通してからコミットする。1つの作業につき1コミットにし、区切りでpushする。
4. 不具合を直したら、同じ不具合を捕まえるテストを足す。
5. `log.md` に、やったこと、結果、失敗、次にやることを数行で書く。
6. 迷ったら、遊べるゲームが前に進む方を選ぶ。通常の技術的な判断は自分で決めて進める。
