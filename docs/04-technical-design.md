# 04 技術設計

## 選定
- TypeScript、Canvas 2D、Vite。ゲームエンジンは導入しない。小さなルールを直接試し、描画負荷を低く保つ。
- ベース解像度 960×540。内部座標を固定し、CSSで画面にフィットさせる。入力座標は内部座標へ変換する。
- 静的サイトとしてビルドし、依存サービス・アカウント・外部通信なしで動作させる。

## 起動と検証の予定コマンド
フェーズ05で `package.json` を追加し、以下を実行可能にする。

| 目的 | コマンド |
| --- | --- |
| 開発 | `npm install` → `npm run dev` |
| 本番ビルド | `npm run build` |
| 型チェック | `npm run typecheck` |
| 単体テスト | `npm test` |

初期テストは純粋関数の衝突判定、武器切替、リトライ時の初期化を優先する。ブラウザでは起動→操作→終了→再挑戦を確認する。CIはゲームループの骨格ができた時点でビルド・型チェック・テストを実行する。

フェーズ05の開発サーバーでは `?autoplay=1` を付けると、繰り返し確認できる自動操作を再生する。本番ビルドでは無効化する。これは描画・進行の確認用で、人の操作感や楽しさを測る代わりにはしない。

## モジュール境界
| 責務 | 方針 |
| --- | --- |
| 状態と進行 | `GameState` と固定のステージイベントを持つ。描画とDOMから独立させる |
| 入力 | キーボード状態をフレームごとの意図に変換。後でタッチ入力を同じ形式へ追加する |
| 更新・衝突 | `update(state, input, dt)` が状態を進め、円形または矩形の単純な当たり判定を使う |
| 描画 | Canvasに状態を描く。テキストHUDは必要に応じDOMへ分離する |
| 音 | ユーザー操作後にだけ開始する独立モジュール。OFFでも視覚情報を維持する |
| UI | タイトル、ポーズ、結果をDOMで表示し、ゲーム進行と分離する |
| 保存 | プロトタイプではなし。MVPで自己ベストを保存する場合は localStorage と破損時初期化を使う |

## 時間とライフサイクル
- `requestAnimationFrame` の時刻から経過時間を計算し、1フレームの更新量を上限付きにする。長いタブ停止から復帰しても敵が一度に進まないようにする。
- 非表示になったら自動ポーズし、復帰は明示操作とする。リトライ時に状態と入力を初期化する。
- リサイズ時は内部座標を変えず表示寸法のみ更新する。高DPI端末ではCanvasピクセルを適切に確保する。
- DOMイベントとゲームループは起動時に一度だけ登録する。

## 既知の設計リスク
- Canvasの描画とDOM操作の座標ずれ。画面サイズ別にクリック／タッチ位置を検証する。
- モバイルでの操作領域不足。フェーズ06以降の実機確認で調整する。
- 仮の数値が切替の利点を作らない可能性。フェーズ05でログを取り調整する。

## フェーズ07時点の実装
ゲーム状態と時刻表は `phase-07-02/src/game.ts`・`stage.ts`、キーボードとタッチの合成は `touch.ts`、Canvas描画とDOM画面遷移は `main.ts`、音は `sound.ts` に分離した。音のON/OFFだけがMVPの設定なので、独立した設定画面は設けず全画面のヘッダーボタンで操作する。保存機能はMVPに必須でないため導入していない。08-02ではCanvas内部座標を960×540に保ち、表示寸法×DPRを実ピクセル数にして描画変換を更新する。実機での視認性評価は引き続き必要。
