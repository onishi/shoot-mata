# Phase 00 — 旧版の反省と再調査

調査日: 2026-10-19

## 結論

ver01の主な失敗は実装力ではなく、**1ステージのMVPを製品要件へ昇格させ、作業工程の終了を製品完成と同一視したこと**にある。QAは丁寧だったが、検査対象そのものが小さすぎた。v02では最初に完成製品の量と質を固定し、プロトタイプ、バーティカルスライス、コンテンツ完成、製品完成を別々のゲートとして扱う。

## ver01で起きたこと

### 1. ユーザーの製品像よりMVP文書が強くなった

- `ver01/docs/02-mvp.md` は1ステージ約3分をMVPとし、追加ステージ、武器追加、複雑な強化を「後回し」にした。
- `ver01/docs/04-task-list.md` の最終検収は、そのMVP条件への合格だけをゴールにした。
- `ver01/docs/10-acceptance.md` も「MVP対応表」で公開可否を判定した。
- `ver01/docs/12-backlog.md` では分岐ルートと複数武器を低優先度の新機能として保留した。

その結果、「多彩なステージ」「特徴的なパワーアップ」は完成条件から消えた。v02ではREADMEと製品要件がMVPより常に上位であり、必須要件をバックログへ降格できない。

### 2. フェーズの通過が品質の代わりになった

`ver01/docs/log.md` はフェーズ12でロードマップ完了を宣言した一方、同じ記録に物理端末の操作感、主観的な楽しさ、音の聴感などの未確認事項を残していた。個々のPLANを閉じることが、当初の製品像を満たすことより優先された。

v02ではフェーズ番号ではなく受け入れマトリクスが完成判定を持つ。Phase 07で4ステージと全パワーアップが揃わなければPhase 08へ進めず、Phase 10ではREADMEの全必須要件を再照合する。

### 3. バーティカルスライスの「完成品質」が低く定義された

ver01のアート方針は「少数の幾何形状」を採用し、レビューも「図形だけで再利用できる」ことを肯定した。これはプロトタイプの視認性検証には有効だが、完成アートの証拠ではない。背景、キャラクター、敵、ボスの造形やアニメーションを量産する工程が存在しなかった。

v02のPhase 04は、完成想定の代表シーンを実際のゲーム内で確認する。アセット台帳は各素材の状態を `planned / draft / final / verified` で追跡し、基本図形や仮素材が必須経路に残ったままコンテンツ完成にできない。

### 4. コアの面白さを未確認のまま拡張した

`ver01/docs/05-prototype-review.md` は「人の連続プレイでの楽しさ・難度は未確認」と明記しつつ次へ進んだ。ワイド／フォーカスは識別できることを確認したが、意味のある選択か、繰り返したいかまでは証明していない。後半は決定的な自動プレイの安定性検証が中心となった。

v02ではPhase 03で最低3案を同じ評価軸で操作比較する。自動プレイは再現性と進行不能検出に使い、楽しさの証拠とはしない。主観評価を実施できない場合は未確認のままゲートを閉じない。

### 5. 同一成果物の複製が進捗量を大きく見せた

ver01はフェーズごとにプロジェクト全体を複製した。履歴保存にはなるが、同じ1ステージを多数のディレクトリで検査する構造となり、コンテンツ量は増えないまま成果物とテスト件数が増えた。

v02は単一の `ver02/game/` を継続的に育てる。フェーズ成果はGit履歴、タグ、文書、データ駆動のステージ定義で追跡し、プロジェクト全体を複製しない。

### 6. 検証の量と対象範囲を混同した

ver01では型検査、ビルド、連続自動クリア、画面サイズ確認を多数実施した。これは価値がある。しかし、それらは1ステージ・2モードの正しさを繰り返し示すもので、4ステージや3武器系統の不在を補えない。

v02の受け入れマトリクスは「要件 → 実装 → 自動テスト → ブラウザ確認 → 証拠」を一行で結び、同じ項目の再確認を新しい機能の完成と数えない。

## ブラウザ制約と設計への影響

| 制約 | 根拠 | v02での扱い |
| --- | --- | --- |
| 音声の自動再生はユーザー操作なしでは拒否され得る | MDN Web Audio | START操作でAudioContextを初期化し、失敗しても無音で開始可能にする |
| `requestAnimationFrame` は高リフレッシュレートで頻度が変わり、背景タブでは停止し得る | MDN | 固定時間刻みのシミュレーション、delta上限、非表示時の自動ポーズを設計する |
| マルチタッチは複数pointerIdの追跡が必要で、既定ジェスチャーと競合する | MDN Pointer Events | Pointer Eventsへ統一し、ゲーム面に限定して `touch-action` を設定。解除・中断をテストする |
| フルスクリーン開始には一時的なユーザー操作が必要 | MDN Fullscreen | 必須にせず明示ボタンから要求し、拒否時も通常表示で遊べる |

## Phase 01へ渡す仮説

3案の詳細は `01-concept.md` で比較する。現時点では選定しない。

1. **三連装リアクター** — 3色のコアを3スロットへ取得順に装填し、先頭色が武器系統、同色数が成長段階、異色が補助特性になる。入れ替えには古いコアの排出という損失がある。
2. **位相航路** — 戦闘中の行動で同じ場所の安全相／高危険相を切り替え、地形、敵、報酬、ボスの攻撃面が変わる。ルート判断を瞬間的な射撃へ接続する。
3. **漂流兵装群** — 敵部品を回収し、自機の周囲へ有限時間の兵装として配置する。位置と熱量を管理し、壊して緊急攻撃へ転用できる。

## Phase 01で答える問い

- 10秒で操作結果が分かり、1分以内に最初の意味ある選択が発生するか。
- 主武器3系統×3段階を、数値差ではなく攻撃範囲・位置取り・危険許容の差として作れるか。
- キーボードとタッチの両方で、同時入力を増やしすぎず扱えるか。
- 4ステージそれぞれの固有仕掛けと相互作用を作れるか。
- 失敗後に別の選択を試す理由があり、上達を説明できるか。
- 既存作品の固有表現を使わず、一枚の画面で本作だと識別できるか。

## Phase 00判定

完了。失敗原因、再発防止策、外部調査、検証仮説が揃った。次はPhase 01で3案を同じ評価軸により比較し、一文コンセプトを1案だけ選ぶ。
