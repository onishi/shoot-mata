# 意思決定記録

## D-001: v02はver01を改修しない

- 日付: 2026-10-19
- 状態: 採用
- 判断: ver01のコード、素材、設定をコピーせず、設計と実装をゼロから作る。
- 理由: 旧構造は1ステージMVPを製品完成とした前提を広範囲に含み、部分改修では同じ範囲縮小を引き継ぐ。
- 影響: ver01は失敗原因と検証手法の参照専用。新成果物は `ver02/` に置く。

## D-002: ゲーム本体をフェーズごとに複製しない

- 日付: 2026-10-19
- 状態: 採用
- 判断: 実装は単一の `ver02/game/` で進め、履歴はGitと文書で保持する。
- 理由: ディレクトリ複製は同一コンテンツの検査回数を増やす一方、製品の量と品質を増やさなかった。
- 影響: 各フェーズのディレクトリにはPLANと証拠への参照を置き、ゲーム一式は置かない。

## D-003: Phase 00ではコンセプトを選ばない

- 日付: 2026-10-19
- 状態: 採用
- 判断: 調査から3仮説を作るが、選定はPhase 01の比較後に行う。
- 理由: 最初に思いついた低コスト案へ固定されたver01の再発を防ぐ。
- 影響: `01-concept.md` は候補状態で開始する。

## D-004: 取得順で組む「三連装リアクター」を製品コンセプトにする

- 日付: 2026-10-19
- 状態: 採用。ただしPhase 03の操作比較で反証可能
- 判断: 3色のコアを3枠へ取得順に装填し、先頭色を主武器、同色数を成長段階、異色を補助特性とする案を採用する。
- 比較: 位相航路はステージ制作が二重化し、漂流兵装群はタッチ操作と小画面の情報量に高いリスクがある。三連装リアクターは3武器×3段階、意味ある取得選択、低い入力数を一つの仕組みで満たせる。
- 影響: Phase 02では取得順、押し出し、3武器系統、異色補助、4ステージとの相互作用を製品要件へ落とす。Phase 03で判断の面白さと視認性を実証できなければ修正または再選定する。

## D-005: 製品版を4ステージのキャンペーンと単独ステージ選択で構成する

- 日付: 2026-10-19
- 状態: 採用
- 判断: 軌道残骸帯、雲海精製塔、生体方舟、恒星炉心の4舞台を順次進むキャンペーンを本編とし、解放済みステージは単独で開始・再挑戦できるようにする。
- 理由: 通し進行と各ステージ単独の受け入れを両立し、色替えではない固有仕掛けを先に製品要件へ固定するため。
- 影響: Phase 06で第1面を完成品質の制作基準にし、Phase 07で残り3面を揃える。4面未達ではPhase 08へ進まない。

## D-006: ゲームパッドとPWAを初回製品の必須範囲に含めない

- 日付: 2026-10-19
- 状態: 採用
- 判断: 必須入力はキーボードとタッチとし、ゲームパッドは追加可能な設計に留める。オフライン対応・インストール可能なPWAも必須にしない。
- 理由: READMEが求める入力・配信形態を満たしつつ、検証対象を完成品質の4ステージへ集中する。どちらも中核メカニクスの成立条件ではない。
- 影響: 入力抽象化と例外安全なローカル保存は必須。追加実装する場合は対応環境とテストを受け入れマトリクスへ増やす。

## D-007: オンライン共有よりローカルな再挑戦情報を優先する

- 日付: 2026-10-19
- 状態: 採用
- 判断: ステージ別・難度別ベストスコア、結果内訳、直前のコア列を必須とし、オンライン順位、スコア共有、リプレイ保存は初回製品の必須にしない。
- 理由: 反復理由を外部サービスに依存させず、失敗から次の具体的な選択へ戻すというコンセプトを直接支えるため。
- 影響: 標準製品は個人情報送信を必要とせず、静的配信とローカル保存だけで成立する。

## D-008: Phase 03は客観比較でFIFO三連装を確定する

- 日付: 2026-10-21
- 状態: 採用
- 判断: 人間による主観評価を進行ゲートから外し、長さ6の全729コア列とCORE-02〜04の機械判定で3方式を比較する。全要件を満たす唯一のFIFO三連装を製品方式として確定する。
- 理由: ユーザーから主観評価を飛ばして進める明示指示があり、FIFOだけが取得順3枠、先頭色と同色数、混色補助と交換代償を同時に満たした。到達可能な戦闘構成もFIFO 18、他方式各9だった。
- 影響: Phase 04へ進む。楽しさ、操作感、聴感などの主観品質は未評価と明記し、機械評価で確認済みとは扱わない。実タッチ端末と別ブラウザの客観確認は後続の製品検証で行う。

## D-009: 保存schemaは破損値を上書きせずメモリへ縮退する

- 日付: 2026-10-21
- 状態: 採用
- 判断: 保存version 1では進行、面・難度別best、設定を分離する。parse、schema、version、migrationの失敗時は原文をrecovery keyへ一度だけ退避し、初期値とメモリ内保存でゲームを継続する。
- 理由: 破損やブラウザの保存拒否を起動不能へせず、原因となった原文を自動上書きから守りながらPROG-05を満たすため。
- 影響: version 0から1への移行経路を回帰テストとして維持する。将来schemaを変更する場合はversionを増やし、段階的migrationと失敗テストを同時に追加する。

## D-010: ステージ固有挙動は登録behaviorと検査済みデータへ分離する

- 日付: 2026-10-21
- 状態: 採用
- 判断: stage schema version 1に背景、敵、drop、連続区間、wave、仕掛け、boss phase、音、遷移を持たせる。固有挙動は種類別の登録済みbehavior IDで参照し、未知field、未登録ID、参照切れ、区間外spawnを読込時に拒否する。
- 理由: 4面を追加するときにstage番号の巨大条件分岐へ密結合せず、データの欠落を実行中ではなく自動検査で発見するため。
- 影響: seedはlaneとdrop選択だけへ注入し、同じstage定義とseedから同じscheduleを再現する。schema変更時はversion更新と移行方針が必要。Phase 05のplaceholder asset IDは完成素材とは数えず、Phase 06〜07で台帳の実IDへ置換する。

## D-011: 被弾は最古コアから失い、空の被弾で残機を失う

- 日付: 2026-10-22
- 状態: Phase 05基盤として採用。Phase 06の決定的バランス検証で数値調整可能
- 判断: 被弾ごとにFIFO列の最古コアを1個排出し、コアが空の状態での被弾だけ残機を1失う。被弾前に青補助があれば、その青コアが同時に排出されても延長無敵を適用する。再挑戦はstage開始時の最低構成へ戻す。
- 理由: 取得順と押し出しの理解を防御にも一貫させ、1回の被弾で成長と残機を同時に失わない回復余地を作るため。補助効果は被弾を契機に発動するため、被弾後の列ではなく被弾直前の列を参照する。
- 影響: ミス、コンティニュー、アシスト難度の初期構成と救済量はPhase 06〜07で同じ規則へ接続し、画面内に喪失理由と直前列を表示する。決定的テストなしに規則を変更しない。

## D-012: 制作原本と配信画像を分離する

- 日付: 2026-10-22
- 状態: 採用
- 判断: 生成・編集・権利追跡の正本は原寸PNGで保持し、静的buildには1280×720の背景WebPと、用途別に縮小したlossless WebPのactor・boss・コアだけを含める。
- 理由: 第1面だけでbuild上限の96%を消費しており、残り3面を必須品質のまま追加できなかった。輪郭素材を可逆、背景をPSNR 33 dB以上・alpha差0として役割別に分けると、第1面の画面品質を数値検査しながら容量を約85%削減できる。
- 影響: 新規画像は `delivery-asset-config.mjs` へ寸法、方式、所属予算を登録し、`npm run assets:optimize` の監査JSONとbuild予算テストを同時に更新する。配信派生物だけを編集せず、変更は原本から再生成する。
